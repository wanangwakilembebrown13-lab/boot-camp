Almost every app you have ever used — Facebook, WhatsApp, your bank — stores its data in a relational database. Instagram keeps users, posts, and likes. Airtel Money keeps accounts, transfers, and balances. Even a small Malawian shop's inventory system is, at its core, a database.

What is a database?

A database is a structured collection of data that a program can read from and write to efficiently. The word relational means the data is organised into tables that relate to each other.

Tables, rows, columns

A table looks just like a spreadsheet:

  • Columns define what kind of data you are storing — name, age, district
  • Rows are individual records — one student, one order, one payment
  • Cells are the intersections — the value at a specific row and column
students
+----+-----------+----------+-------+----------+
| id | first_name| last_name| grade | district |
+----+-----------+----------+-------+----------+
|  1 | Chisomo   | Banda    |    10 | Lilongwe |
|  2 | Tadala    | Mwale    |    10 | Blantyre |
|  3 | Gift      | Phiri    |    11 | Mzuzu    |
+----+-----------+----------+-------+----------+

The difference between a database and a spreadsheet is how you query it. A spreadsheet is designed for a human to look at. A database is designed for a program to ask questions: "How many students are in Form 3?", "Which district has the highest average grade?"

SQL — the language of databases

SQL (pronounced "sequel" or "S-Q-L") stands for Structured Query Language. It is how you talk to every major database — PostgreSQL, MySQL, SQL Server, Oracle, SQLite. Learn one, and the same skills transfer to all of them.

SQL splits into four families:

  • SELECT — read data
  • INSERT — add new rows
  • UPDATE — change existing rows
  • DELETE — remove rows

That is 90% of what developers actually write.

Why not just use a spreadsheet?

Because spreadsheets break down at scale:

  • Ten thousand rows is fine. Ten million rows is not.
  • Two people editing simultaneously corrupts the file.
  • There is no access control — everyone with the file sees everything.
  • Relationships between tables are ad-hoc and error-prone.

A database handles all of this cleanly.

The course database: Throughout this course, we will work with a Malawi school management database. It has four tables: students, teachers, classes, and enrollments. Every lesson adds to what you can do with it.

A single table is fine for toy data. Real data has relationships — a student enrolls in many classes, a class is taught by one teacher, an order contains many items. That is what makes databases relational.

Primary keys

Every table needs a way to identify each row uniquely. That is the primary key.

CREATE TABLE students (
  id INTEGER PRIMARY KEY,
  first_name TEXT NOT NULL,
  last_name TEXT NOT NULL
);

Rules of a primary key:

  • Every row must have one
  • No two rows can share the same value
  • It never changes once assigned

The most common pattern is an integer called id that auto-increments (1, 2, 3, 4...).

Foreign keys

A foreign key is a column that points to a primary key in another table. It is how two tables are connected.

CREATE TABLE classes (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  teacher_id INTEGER NOT NULL,
  FOREIGN KEY (teacher_id) REFERENCES teachers(id)
);

Here, teacher_id in classes points to id in teachers. Every class must have a teacher. If you try to insert a class with a teacher_id that does not exist in teachers, the database rejects it.

Why this matters

Foreign keys enforce referential integrity — the guarantee that data stays consistent. Without them, you could end up with classes assigned to teachers who do not exist. With them, that is impossible.

One-to-many relationships

The most common shape in relational data:

teachers      1 ──── many  classes
students      1 ──── many  enrollments
classes       1 ──── many  enrollments

One teacher teaches many classes. One student has many enrollments. This is expressed by putting the foreign key on the "many" side. classes.teacher_id is a foreign key because one teacher has many classes.

Many-to-many relationships

Sometimes two tables need a many-to-many relationship: one student is in many classes, and one class has many students. This is expressed with a join table.

CREATE TABLE enrollments (
  id INTEGER PRIMARY KEY,
  student_id INTEGER NOT NULL,
  class_id INTEGER NOT NULL,
  term TEXT NOT NULL,
  FOREIGN KEY (student_id) REFERENCES students(id),
  FOREIGN KEY (class_id) REFERENCES classes(id)
);

enrollments is the join table. It sits between students and classes and holds one row for every student-class pairing.

Rule of thumb: if you ever catch yourself storing multiple values in one cell (like "Chisomo, Tadala, Gift" in a column called students), stop. That is a relationship that needs its own table. Databases hate comma-separated lists.

SELECT is the SQL statement you will write more than all others combined. It reads data. Nothing changes. Nothing is destroyed. You can run it a million times safely.

The simplest form

SELECT * FROM students;

The * means "all columns". The FROM students tells SQL which table to read from. The semicolon marks the end of the statement — every SQL statement ends with one.

Choosing specific columns

SELECT first_name, last_name FROM students;

Comma-separated list of columns. This is almost always better than SELECT * — it is clearer and faster.

Adding column aliases

SELECT
  first_name AS "First Name",
  last_name AS "Last Name"
FROM students;

AS gives a column a different name in the output. Use it when the raw column name is unclear, or when you want formatted headers.

ORDER BY

SELECT first_name, grade FROM students
ORDER BY grade DESC;

Sorts the results. ASC (ascending) is the default; DESC reverses it. You can sort by multiple columns:

SELECT first_name, grade, district FROM students
ORDER BY grade DESC, first_name ASC;

Sort by grade first. If two students share a grade, sort them alphabetically.

LIMIT

SELECT * FROM students LIMIT 5;

Returns only the first 5 rows. Useful for previewing a table without dumping ten thousand rows.

DISTINCT

SELECT DISTINCT district FROM students;

Returns only unique values. If 6 students are from Lilongwe, "Lilongwe" appears once.

Combining them

SELECT DISTINCT district
FROM students
ORDER BY district ASC
LIMIT 10;

Reads as: "give me the ten distinct districts, alphabetically."

Clause order matters. SQL requires SELECT ... FROM ... WHERE ... GROUP BY ... ORDER BY ... LIMIT in that order. Get it wrong and SQL will tell you. The order is not optional.

SELECT * FROM students returns everything. Real queries need to filter. That is what WHERE does.

The basic filter

SELECT first_name, last_name, district
FROM students
WHERE district = 'Lilongwe';

Returns only students from Lilongwe. Notice strings use single quotes. Numbers do not:

SELECT * FROM students WHERE grade = 10;

Comparison operators

  • = equal to
  • != or <> not equal to
  • < less than
  • > greater than
  • <=, >= less/greater or equal
SELECT * FROM students WHERE grade > 10;
SELECT * FROM enrollments WHERE grade_percent >= 80;

AND, OR, NOT

SELECT * FROM students
WHERE grade = 10 AND district = 'Lilongwe';

SELECT * FROM students
WHERE district = 'Lilongwe' OR district = 'Blantyre';

Wrap conditions in parentheses when you mix AND with OR — otherwise SQL's precedence rules will surprise you:

SELECT * FROM students
WHERE grade = 10 AND (district = 'Lilongwe' OR district = 'Blantyre');

IN and BETWEEN

SELECT * FROM students
WHERE district IN ('Lilongwe', 'Blantyre', 'Mzuzu');

SELECT * FROM enrollments
WHERE grade_percent BETWEEN 70 AND 90;

IN is a cleaner way to write a long OR chain. BETWEEN is inclusive on both ends — 70 and 90 are included.

LIKE — pattern matching

SELECT * FROM students WHERE first_name LIKE 'Ch%';
SELECT * FROM students WHERE last_name LIKE '%a';

% matches any number of characters. So 'Ch%' matches Chisomo, Chikondi, Chimwemwe — anything starting with "Ch". '%a' matches names ending in "a".

Handling NULL

NULL means "no value". It is not zero and it is not an empty string. You cannot compare NULL with =. You must use IS NULL or IS NOT NULL.

SELECT * FROM enrollments WHERE grade_percent IS NULL;
SELECT * FROM enrollments WHERE grade_percent IS NOT NULL;

This is one of the most common mistakes for beginners: writing WHERE column = NULL never returns anything.

ORDER BY with WHERE

SELECT first_name, grade FROM students
WHERE district = 'Lilongwe'
ORDER BY grade DESC, first_name ASC;

Filter first, then sort. That is the natural reading order.

Real query, real question: "List every Form 10 student from Lilongwe, sorted by first name." That is a WHERE, an ORDER BY, and a column selection — the three core tools of reading data.

Reading is only half of SQL. Eventually you need to add new rows, change existing ones, and remove old ones. That is INSERT, UPDATE, and DELETE.

INSERT — adding data

INSERT INTO students (first_name, last_name, grade, district, enrolled_year)
VALUES ('Mphatso', 'Chirwa', 10, 'Zomba', 2024);

You list the columns you are providing, then the values in the same order. Columns you skip are filled with NULL or their default.

Inserting multiple rows in one statement:

INSERT INTO students (first_name, last_name, grade, district, enrolled_year) VALUES
  ('Alinafe', 'Nkosi', 9, 'Blantyre', 2024),
  ('Blessings', 'Kalulu', 11, 'Lilongwe', 2022),
  ('Chifundo', 'Zimba', 10, 'Mzuzu', 2023);

Faster, and it either all succeeds or all fails. No half-inserted rows.

UPDATE — changing data

UPDATE students
SET district = 'Lilongwe'
WHERE id = 4;

Read it as: "change the district column to 'Lilongwe' for the row where id is 4."

Multiple columns at once:

UPDATE students
SET district = 'Zomba', grade = 10
WHERE id = 4;

⚠️ Always use WHERE with UPDATE

This is the single most important rule in SQL:

UPDATE students SET district = 'Lilongwe';   -- ⚠️ Changes EVERY row!

Without a WHERE clause, UPDATE affects every single row in the table. Every student now claims to be from Lilongwe. There is no undo. You cannot Ctrl+Z a database.

The same applies to DELETE:

DELETE FROM students WHERE id = 4;

Deletes the one student with id 4.

DELETE FROM students;   -- ⚠️ Deletes ALL students. No warning. No undo.

Professional teams often work in transactions precisely so that a mis-typed WHERE can be rolled back. For now, the rule is simpler: write the WHERE first, then write the UPDATE.

The safe pattern

  1. Write the WHERE clause first: WHERE id = 4
  2. Test it with a SELECT: SELECT * FROM students WHERE id = 4; — does it return exactly the rows you meant?
  3. If yes, convert the SELECT into an UPDATE

This five-second habit will save you weeks of pain over your career.

Soft deletes

In real production systems, DELETE is often avoided entirely. Instead, a column like deleted_at is set to the current timestamp, and every query adds WHERE deleted_at IS NULL.

UPDATE students SET deleted_at = CURRENT_TIMESTAMP WHERE id = 4;

SELECT * FROM students WHERE deleted_at IS NULL;

This lets you "undo" a delete. Banks, hospitals, and government systems almost always work this way.

The discipline: every UPDATE and DELETE should have a WHERE. If you find yourself typing one without a WHERE, stop and ask whether you really mean to affect every row.

The real power of a relational database comes from joining tables. You store data across multiple tables to avoid duplication, then combine them when you need to read.

The problem

Look at the enrollments table:

+----+------------+----------+--------+---------------+
| id | student_id | class_id | term   | grade_percent |
+----+------------+----------+--------+---------------+
|  1 |          1 |        1 | Term 1 |            78 |
|  2 |          1 |        2 | Term 1 |            85 |
+----+------------+----------+--------+---------------+

It stores student_id, not the student's name. That is deliberate — if Chisomo changes her name, we update it in one place, not in every enrollment row.

But when we read, we want to see the name, not the number. That is what JOIN is for.

INNER JOIN

SELECT
  s.first_name,
  s.last_name,
  c.name AS class_name,
  e.grade_percent
FROM enrollments e
JOIN students s ON e.student_id = s.id
JOIN classes c ON e.class_id = c.id;

Let's unpack that:

  • FROM enrollments e — start with the enrollments table, and give it the alias e
  • JOIN students s ON e.student_id = s.id — for every enrollment, find the matching student and give that table the alias s
  • JOIN classes c ON e.class_id = c.id — same for the class
  • s.first_name — read the first_name column from the students table (aliased s)

The result is one row per enrollment, with the student's name and the class name included.

Table aliases

You do not have to use aliases, but you should. Without them you have to write:

SELECT enrollments.grade_percent
FROM enrollments
JOIN students ON enrollments.student_id = students.id;

Aliases are shorter, clearer, and standard practice.

INNER vs LEFT JOIN

  • INNER JOIN — only returns rows where the join finds a match on both sides. If a student has no enrollments, that student does not appear.
  • LEFT JOIN — returns every row from the left table, plus any matches from the right. If a student has no enrollments, they still appear, but with NULL in the enrollment columns.

This distinction matters a lot. Consider "list every student and their classes":

-- INNER JOIN — silently drops students with no enrollments
SELECT s.first_name, c.name
FROM students s
JOIN enrollments e ON s.id = e.student_id
JOIN classes c ON e.class_id = c.id;

-- LEFT JOIN — keeps every student
SELECT s.first_name, c.name
FROM students s
LEFT JOIN enrollments e ON s.id = e.student_id
LEFT JOIN classes c ON e.class_id = c.id;

If you are asking "how many students have enrolled in at least one class?" the INNER JOIN gives you the right numerator. If you are asking "which students have enrolled in nothing?" you need the LEFT JOIN and a WHERE clause checking for NULL.

A common trap

If you ever see a query returning fewer rows than you expected, check your JOINs. An INNER JOIN quietly drops any row that has no match on the other side.

The mental model: imagine placing all tables side by side, and drawing lines from the foreign key in one table to the primary key in another. A JOIN walks those lines and merges the matched rows.

So far every query returns individual rows. But most business questions are not about individual rows. They are about counts, sums, and averages. That is what aggregation is for.

The five aggregate functions

  • COUNT() — how many rows
  • SUM() — total
  • AVG() — mean
  • MIN() — smallest
  • MAX() — largest
SELECT COUNT(*) FROM students;
SELECT AVG(grade_percent) FROM enrollments;
SELECT MIN(grade_percent), MAX(grade_percent) FROM enrollments;

GROUP BY — the real superpower

An aggregate on its own gives you one number. GROUP BY lets you compute that number for each category.

SELECT district, COUNT(*) AS student_count
FROM students
GROUP BY district
ORDER BY student_count DESC;

Read it as: "for each district, count the students, then sort by count descending."

The rule: everything in the SELECT list must either be in the GROUP BY, or inside an aggregate function. This is not a style choice — it is what SQL requires.

-- ✅ Correct
SELECT district, AVG(grade) FROM students GROUP BY district;

-- ❌ Error: first_name is neither grouped nor aggregated
SELECT district, first_name, AVG(grade) FROM students GROUP BY district;

Multiple groups

SELECT district, grade, COUNT(*) AS n
FROM students
GROUP BY district, grade
ORDER BY district, grade;

This gives one row per (district, grade) pair. If Lilongwe has three Grade 10 students and two Grade 11, you get two rows for Lilongwe.

HAVING — filtering groups

WHERE filters rows before aggregation. HAVING filters groups after aggregation.

SELECT district, COUNT(*) AS student_count
FROM students
GROUP BY district
HAVING COUNT(*) > 2;

Read it as: "count students per district, then keep only the districts with more than 2 students." You cannot use WHERE for that, because WHERE runs before the aggregation.

Real business queries

-- Total enrollments per class
SELECT c.name, COUNT(*) AS enrollments
FROM classes c
JOIN enrollments e ON e.class_id = c.id
GROUP BY c.name
ORDER BY enrollments DESC;
-- Average grade per class
SELECT c.name, ROUND(AVG(e.grade_percent), 1) AS avg_grade
FROM classes c
JOIN enrollments e ON e.class_id = c.id
GROUP BY c.name
ORDER BY avg_grade DESC;
-- Top-performing students (students with an average grade above 80)
SELECT s.first_name, s.last_name, ROUND(AVG(e.grade_percent), 1) AS avg_grade
FROM students s
JOIN enrollments e ON e.student_id = s.id
GROUP BY s.id
HAVING AVG(e.grade_percent) > 80
ORDER BY avg_grade DESC;

That last query joins two tables, groups by student, filters groups with a HAVING clause, and sorts by the aggregate. If you can write that, you can answer most real database questions.

The clause order, again: SELECT ... FROM ... JOIN ... WHERE ... GROUP BY ... HAVING ... ORDER BY ... LIMIT. WHERE filters rows. GROUP BY creates groups. HAVING filters groups. The order is not optional.

Writing queries is one skill. Designing the tables so that queries are easy and data stays clean is another. That is what schema design is about.

What is normalization?

Normalization is a set of rules for organising tables to reduce duplication and avoid inconsistency. The three forms you need to know:

First Normal Form (1NF)

Every cell holds one value. No comma-separated lists.

-- ❌ Bad: multiple teachers in one cell
+----+------------+--------------------------------+
| id | name       | teachers                       |
+----+------------+--------------------------------+
|  1 | Form 1     | Mr. Banda, Mrs. Phiri          |
+----+------------+--------------------------------+

The right design gives every class-teacher pairing its own row in a join table.

Second Normal Form (2NF)

Every non-key column depends on the whole primary key, not part of it. In practice: when you have a join table, do not store attributes of the joined entities inside it.

-- ❌ Bad: student_name depends on student_id, not on the whole enrollment key
+----+------------+----------+---------------+---------------+
| id | student_id | class_id | student_name  | grade_percent |
+----+------------+----------+---------------+---------------+
|  1 |          1 |        1 | Chisomo Banda |            78 |
+----+------------+----------+---------------+---------------+

Storing student_name here means every enrollment row repeats the name. If Chisomo changes her name, you must update dozens of rows. Worse: if you forget one, the database now disagrees with itself.

The fix: keep student_name only in students, and use student_id here.

Third Normal Form (3NF)

No transitive dependencies. If a column depends on another non-key column, it belongs in its own table.

-- ❌ Bad: district_region depends on district, not on student
+----+------------+----------+------------------+
| id | first_name | district | district_region  |
+----+------------+----------+------------------+
|  1 | Chisomo    | Lilongwe | Central          |
+----+------------+----------+------------------+

Lilongwe is always in the Central region. Storing that fact on every student row is duplication. Move it to a districts table with a region column, and reference it by district_id.

When NOT to normalize

Normalization is the right default, but there are cases where you deliberately denormalize:

  • Reporting databases. A data warehouse often stores pre-computed aggregates for speed.
  • Frequently read columns. If a join is expensive and the data rarely changes, duplicating one column can be worth it.
  • Snapshots. An invoice stores the price at the time of sale, not the current product price. This is duplication on purpose.

The rule: normalize until it hurts, denormalize until it works.

You have written queries. They work. But how fast are they on a million rows? That is what indexing is about.

The problem

Imagine a table with one million students. You write:

SELECT * FROM students WHERE last_name = 'Banda';

Without an index, SQLite reads every row, checking each one. One million reads. It is called a full table scan, and it is slow.

What an index is

An index is a sorted structure that points to rows. It is exactly like the index at the back of a textbook — instead of reading every page to find "photosynthesis", you jump straight to page 247.

CREATE INDEX idx_students_last_name ON students(last_name);

Now the same query is nearly instant. SQLite finds "Banda" in the index, follows the pointer, and retrieves the rows.

When indexes help

Add an index on:

  • Columns used in WHERE clauses — WHERE last_name = 'Banda'
  • Columns used in JOIN conditions — foreign keys
  • Columns used in ORDER BY — sorting a million rows is expensive

Foreign keys are usually the highest-impact place to index. Most JOIN queries collapse to near-instant with the right indexes on the join columns.

When indexes hurt

Every index has a cost:

  • They take disk space. Each index is essentially a second copy of the indexed data.
  • They slow down writes. Every INSERT, UPDATE, and DELETE must also update every index on that table.

So: index the columns you filter on and join on. Do not index everything.

Composite indexes

An index can span multiple columns:

CREATE INDEX idx_students_district_grade ON students(district, grade);

This index helps queries like:

SELECT * FROM students WHERE district = 'Lilongwe' AND grade = 10;

But NOT queries that only filter on grade. The rule: a composite index helps queries that filter on a left-prefix of the indexed columns. (district, grade) helps (district) and (district, grade), but not (grade) alone.

EXPLAIN — the query planner's report

Every database has a way to show you what it does with a query. In SQLite:

EXPLAIN QUERY PLAN
SELECT * FROM students WHERE last_name = 'Banda';

You will see either "SCAN students" (bad — reading every row) or "SEARCH students USING INDEX idx_students_last_name" (good — using the index).

Get in the habit of running EXPLAIN QUERY PLAN on any query you think might be slow. It is the single most useful diagnostic tool for database performance.

Query optimisation checklist

  • Are the columns in WHERE indexed?
  • Are the JOIN columns indexed?
  • Are you using SELECT * when you only need a few columns?
  • Are you filtering rows as early as possible?
  • Could a GROUP BY be avoided by adding a summary table?
Premature optimization is the root of all evil. Do not add indexes "just in case." Add them when EXPLAIN QUERY PLAN tells you a query is doing a full table scan on a table that matters. Then measure again.

Time to build. Over the next two lessons, you will design and query a database for a real Malawi business scenario.

The scenario

You are building the database for a small agri-business in Kasungu that buys maize from farmers and sells it to traders. They need to track:

  • Farmers — name, village, phone
  • Deliveries — farmer, date, weight in kg, price per kg
  • Buyers — name, company, phone
  • Sales — buyer, date, weight in kg, price per kg

Design the schema

Before touching the editor, answer these questions on paper:

  1. What are the four tables?
  2. What is the primary key of each?
  3. Where do the foreign keys go?
  4. What type should each column have? (INTEGER, TEXT, REAL, DATE)

Rules to remember:

  • Farmers do not appear directly in sales. Sales reference buyers. The farmer relationship is on the delivery side.
  • Never store a farmer's name inside the deliveries table — use farmer_id.
  • Weight and price are numbers. Use REAL for decimals, INTEGER for whole numbers.
  • Dates can be stored as TEXT in ISO format (YYYY-MM-DD), which sorts correctly.

Write the CREATE statements

CREATE TABLE farmers (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,
  village TEXT,
  phone TEXT
);

CREATE TABLE buyers (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,
  company TEXT,
  phone TEXT
);

CREATE TABLE deliveries (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  farmer_id INTEGER NOT NULL,
  delivery_date TEXT NOT NULL,
  weight_kg REAL NOT NULL,
  price_per_kg REAL NOT NULL,
  FOREIGN KEY (farmer_id) REFERENCES farmers(id)
);

CREATE TABLE sales (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  buyer_id INTEGER NOT NULL,
  sale_date TEXT NOT NULL,
  weight_kg REAL NOT NULL,
  price_per_kg REAL NOT NULL,
  FOREIGN KEY (buyer_id) REFERENCES buyers(id)
);

The design is 80% of the work. Once the tables exist, the queries almost write themselves. If you find yourself writing a query that feels awkward, the schema is probably wrong.

Your tables are ready. Now you answer the business questions. Every query in this lesson is one the owner of that agri-business would actually ask.

Question 1 — How much maize did each farmer deliver?

SELECT
  f.name,
  SUM(d.weight_kg) AS total_kg,
  ROUND(SUM(d.weight_kg * d.price_per_kg), 2) AS total_paid
FROM farmers f
JOIN deliveries d ON d.farmer_id = f.id
GROUP BY f.id
ORDER BY total_kg DESC;

This joins farmers to deliveries, groups by farmer, sums the weight, and computes how much was paid. SUM(d.weight_kg * d.price_per_kg) is a computed column inside an aggregate — completely valid and very useful.

Question 2 — What was the total profit?

SELECT
  (SELECT SUM(weight_kg * price_per_kg) FROM sales) -
  (SELECT SUM(weight_kg * price_per_kg) FROM deliveries) AS profit;

Subqueries in the SELECT list let you compute one value from another query. The profit is total sales minus total deliveries.

Question 3 — Which buyer spent the most?

SELECT
  b.name,
  b.company,
  SUM(s.weight_kg * s.price_per_kg) AS total_spent
FROM buyers b
JOIN sales s ON s.buyer_id = b.id
GROUP BY b.id
ORDER BY total_spent DESC
LIMIT 1;

Question 4 — Average price per kg paid to farmers vs. received from buyers

SELECT
  (SELECT AVG(price_per_kg) FROM deliveries) AS avg_buy_price,
  (SELECT AVG(price_per_kg) FROM sales) AS avg_sell_price,
  (SELECT AVG(price_per_kg) FROM sales) -
  (SELECT AVG(price_per_kg) FROM deliveries) AS margin_per_kg;

This tells the owner the average markup. If the margin is thin, they need to negotiate better sale prices or reduce costs.

Question 5 — Monthly totals

SELECT
  SUBSTR(delivery_date, 1, 7) AS month,
  COUNT(*) AS deliveries,
  ROUND(SUM(weight_kg), 1) AS total_kg
FROM deliveries
GROUP BY SUBSTR(delivery_date, 1, 7)
ORDER BY month;

SUBSTR(delivery_date, 1, 7) extracts the "YYYY-MM" part from an ISO date. Grouping by it gives monthly totals. This is the standard way to build trend reports.
