Flutter uses a language called Dart. It was created by Google and looks a lot like a mix of JavaScript and Java. If you already know JavaScript, you are 80% of the way there — the syntax is close, the concepts are the same.

Variables

In Dart, you declare a variable with a type or with var:

var name = 'Chisomo';       // inferred as String
String city = 'Lilongwe';   // explicit type
int age = 22;
double height = 1.75;
bool isStudent = true;

Prefer var when the type is obvious, and explicit types when it helps readability. Dart is statically typed — the compiler catches type errors before the code even runs.

final and const

final name = 'Chisomo';   // set once, at runtime
const pi = 3.14;          // compile-time constant

Use final for values that are set once but computed at runtime. Use const for true constants that never change.

String interpolation

Dart uses $ inside strings — same idea as JavaScript template literals:

var name = 'Chisomo';
var age = 22;
print('Hello, $name! You are $age.');
print('Next year: ${age + 1}.');

Functions

int add(int a, int b) {
  return a + b;
}

String greet(String name) => 'Hello, $name!';   // arrow syntax

void log(String msg) {
  print(msg);
}

Return type comes first, then the name, then parameters. void means "returns nothing".

Lists and maps

var fruits = ['apple', 'banana', 'mango'];
fruits.add('orange');
print(fruits[0]);          // "apple"
print(fruits.length);      // 4

var user = {
  'name': 'Chisomo',
  'age': 22,
  'city': 'Lilongwe'
};
print(user['name']);       // "Chisomo"

Control flow

Everything you know from JavaScript works here — with slight syntax differences:

if (age >= 18) {
  print('Adult');
} else {
  print('Minor');
}

for (var i = 0; i < 5; i++) {
  print(i);
}

for (var fruit in fruits) {
  print(fruit);
}
In the sandbox below, we run a JavaScript-flavored version of Dart so you can practise instantly without installing anything. The syntax is 95% identical — only differences are noted in each lesson. When you're ready to run real Flutter, install the SDK and use the code exactly as shown in the reading.

A Flutter app is built from widgets. Every visible thing — text, buttons, images, layouts, even the app itself — is a widget. Widgets nest inside each other to form a tree.

Your first app

The absolute minimum Flutter app:

import 'package:flutter/material.dart';

void main() {
  runApp(
    MaterialApp(
      home: Scaffold(
        appBar: AppBar(title: Text('My App')),
        body: Center(
          child: Text('Hello, Malawi!'),
        ),
      ),
    ),
  );
}

Five widgets in play:

  • MaterialApp — the root. Sets up theming, routing, and the Material Design language.
  • Scaffold — a screen with a standard layout. Provides slots for app bar, body, floating action button, etc.
  • AppBar — the top bar. Takes a title widget.
  • Center — centers its child.
  • Text — draws text.

runApp

runApp() is the entry point. It takes one widget — the root of your tree — and hands it to Flutter, which renders everything for you.

Widgets all the way down

Everything is a widget: the app itself, the layout containers, the text, the padding. Widgets are nested to compose more complex UI. A layout is just a tree of small widgets.

Stateless by default

A widget that never changes is called stateless. Its appearance is entirely determined by the arguments you pass in. This is the simplest kind of widget — you just write a function that returns the tree.

Material vs Cupertino

Flutter ships two design systems:

  • Material — Google's design language (Android-like). Used by MaterialApp.
  • Cupertino — Apple's iOS design language. Used by CupertinoApp.

Both work on both platforms. Most apps pick Material — it's more flexible and more widely documented.

You will spend the next 12 weeks learning widgets. Every single lesson adds a few more to your vocabulary. By the end you will compose them without thinking.

Before you can build layouts, you need to know the basic building blocks. This lesson covers the four widgets you will use in almost every screen.

Text

Text('Hello, Malawi!')
Text('Big heading', style: TextStyle(fontSize: 28, fontWeight: FontWeight.bold))
Text('Red text', style: TextStyle(color: Colors.red))

Text takes a positional string and an optional style. TextStyle controls color, size, weight, italics, and more.

Container

A Container is a box. It can have a background color, padding, margin, border, rounded corners, and a fixed size:

Container(
  width: 200,
  height: 100,
  color: Colors.blue,
  child: Text('Inside a box'),
)

If you only need spacing, use Padding or SizedBox instead — they're cheaper.

Padding

Padding(
  padding: EdgeInsets.all(16),
  child: Text('Padded text'),
)

Common EdgeInsets forms:

  • EdgeInsets.all(n) — same on all sides
  • EdgeInsets.symmetric(horizontal: 16, vertical: 8)
  • EdgeInsets.only(left: 20, top: 10)

Center

Centers its child both horizontally and vertically inside the available space:

Center(
  child: Text('Dead center'),
)

Combining them

Center(
  child: Container(
    padding: EdgeInsets.all(24),
    decoration: BoxDecoration(
      color: Colors.blue,
      borderRadius: BorderRadius.circular(16),
    ),
    child: Text(
      'Welcome to Flutter',
      style: TextStyle(color: Colors.white, fontSize: 18),
    ),
  ),
)

That's a card-like box, centered on screen, with a rounded blue background. Twelve lines of Flutter, and it works on every screen size.

Every widget takes a child or children. When you see an error saying "child was not found", it means you passed nothing where a widget was expected.

Single widgets are useful. Layout widgets — Column, Row, and ListView — are how you compose them into screens.

Column — stack vertically

Column(
  children: [
    Text('First'),
    Text('Second'),
    Text('Third'),
  ],
)

Children stack top to bottom. By default, they hug the top-left of the available space.

Row — stack horizontally

Row(
  children: [
    Icon(Icons.star),
    Text('Favorite'),
  ],
)

Children flow left to right.

Alignment

Both Column and Row accept:

  • mainAxisAlignment — along the main axis (vertical for Column, horizontal for Row): start, center, end, spaceBetween, spaceAround
  • crossAxisAlignment — along the cross axis: start, center, end, stretch
Column(
  mainAxisAlignment: MainAxisAlignment.center,
  crossAxisAlignment: CrossAxisAlignment.start,
  children: [ ... ],
)

Padding and spacing

Wrap children in Padding for spacing, or use a SizedBox between items:

Column(
  children: [
    Text('Title'),
    SizedBox(height: 16),
    Text('Subtitle'),
  ],
)

SizedBox(height: 16) inserts vertical space. It's the Flutter way of saying "add a gap here".

ListView — scrolling lists

A Column can't scroll. For long or dynamic lists, use a ListView:

ListView(
  children: [
    ListTile(title: Text('Item 1')),
    ListTile(title: Text('Item 2')),
    ListTile(title: Text('Item 3')),
  ],
)

Or build the list from data — the real-world pattern:

var items = ['Apple', 'Banana', 'Mango'];
ListView(
  children: items.map((fruit) => ListTile(title: Text(fruit))).toList(),
)

Flutter's .map().toList() is how you transform data into widgets. Exactly like React's .map() — same idea, no key prop needed (Flutter handles it differently).

When your Column overflows the screen, Flutter shows a yellow-and-black striped warning. The fix: switch to ListView or wrap in SingleChildScrollView.

Everything so far has been stateless — the UI never changes. Real apps have counters, forms, and dynamic data. That's what state is for.

The problem

If you try to change a variable inside a stateless widget, nothing happens on screen. Flutter doesn't know it needs to redraw. You need to tell it.

StatefulWidget

Real Flutter uses a class with a setState method:

class Counter extends StatefulWidget {
  @override
  State<Counter> createState() => _CounterState();
}

class _CounterState extends State<Counter> {
  int count = 0;

  void increment() {
    setState(() {
      count++;
    });
  }

  @override
  Widget build(BuildContext context) {
    return Column(
      mainAxisAlignment: MainAxisAlignment.center,
      children: [
        Text('Count: $count'),
        ElevatedButton(
          onPressed: increment,
          child: Text('+1'),
        ),
      ],
    );
  }
}

Three parts:

  1. The widget class — its only job is to create the state.
  2. The state class — holds the data (count) and the build method that draws it.
  3. setState — the signal to Flutter: "something changed, redraw".

Why setState matters

If you write count++ without setState, the number changes in memory but the screen does not update. setState tells Flutter to re-run build and update the UI.

In the sandbox

The sandbox uses a slightly simplified form — instead of two classes, you call a StatefulWidget helper with an initial state and a build function:

function Counter() {
  return StatefulWidget({
    initState: () => ({ count: 0 }),
    build: (state, setState) => Column({
      mainAxisAlignment: 'center',
      children: [
        Text('Count: ' + state.count),
        ElevatedButton({
          onPressed: () => setState(() => state.count++),
          child: Text('+1'),
        }),
      ],
    }),
  });
}

Same concepts, less boilerplate. When you install real Flutter, use the class form.

Rule of thumb: if a widget's appearance never changes, use stateless. If it changes because of user action, a timer, or data arriving, use stateful.

Forms are how you collect text from users. In Flutter, the main tool is TextField, and text is usually managed with a TextEditingController.

TextField basics

TextField(
  decoration: InputDecoration(
    labelText: 'Your name',
    hintText: 'e.g. Chisomo',
    border: OutlineInputBorder(),
  ),
)

TextField draws an editable input. The decoration controls the label, hint, border, and icon.

Reading what was typed — onChanged

The simplest approach: listen for changes and store the value in state:

class NameForm extends StatefulWidget {
  @override
  State<NameForm> createState() => _NameFormState();
}

class _NameFormState extends State<NameForm> {
  String name = '';

  @override
  Widget build(BuildContext context) {
    return Column(
      children: [
        TextField(
          decoration: InputDecoration(labelText: 'Name'),
          onChanged: (value) {
            setState(() {
              name = value;
            });
          },
        ),
        Text('Hello, $name!'),
      ],
    );
  }
}

Every keystroke calls onChanged with the current value. We store it in name and setState so the greeting updates live.

TextEditingController

The more powerful pattern uses a controller:

final controller = TextEditingController();

TextField(controller: controller)

// Later, read or clear:
print(controller.text);
controller.clear();

Controllers let you read the value outside the widget, pre-fill it, or clear it programmatically. Use one when you need that control.

Buttons

ElevatedButton(
  onPressed: () {
    print('Pressed!');
  },
  child: Text('Submit'),
)

TextButton(
  onPressed: () {},
  child: Text('Cancel'),
)

IconButton(
  onPressed: () {},
  icon: Icon(Icons.add),
)

ElevatedButton has a filled background, TextButton is flat, IconButton is a tappable icon. All take onPressed.

If onPressed: null (or nothing), the button is disabled. That is the way to grey out a button until a form is valid.

Real apps have multiple screens. Flutter uses a stack of routes — you push new screens on top, and pop them off to go back.

Navigator.push

Push a new screen on top:

Navigator.push(
  context,
  MaterialPageRoute(builder: (context) => DetailScreen()),
);

Two arguments:

  • context — tells Flutter where in the widget tree you are
  • MaterialPageRoute — a builder that returns the widget to show

Going back — Navigator.pop

Navigator.pop(context);

Pops the current screen off the stack and returns to the previous one. Flutter automatically shows a back arrow on the app bar if there's a screen below.

A two-screen app

class HomeScreen extends StatelessWidget {
  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: Text('Home')),
      body: Center(
        child: ElevatedButton(
          onPressed: () {
            Navigator.push(
              context,
              MaterialPageRoute(builder: (c) => DetailScreen()),
            );
          },
          child: Text('Open detail'),
        ),
      ),
    );
  }
}

class DetailScreen extends StatelessWidget {
  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: Text('Detail')),
      body: Center(
        child: ElevatedButton(
          onPressed: () => Navigator.pop(context),
          child: Text('Back'),
        ),
      ),
    );
  }
}

Named routes

For larger apps, register named routes once and push them by name:

MaterialApp(
  routes: {
    '/': (context) => HomeScreen(),
    '/detail': (context) => DetailScreen(),
    '/settings': (context) => SettingsScreen(),
  },
)

// Somewhere:
Navigator.pushNamed(context, '/settings');

Named routes keep navigation logic out of individual widgets. Useful once you have more than three screens.

The route stack is just an array. push adds to the top, pop removes from the top. Every mobile app you have ever used works this way — Android's back button, iOS's swipe gesture, all just pop the top route.

Opening a blank screen is not useful. Navigation is really about passing data — the ID of a product, the name of a user, the result of a form.

Passing data via constructor

The most common way: give the target widget a constructor parameter:

class DetailScreen extends StatelessWidget {
  final String name;
  final int age;

  DetailScreen({required this.name, required this.age});

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: Text(name)),
      body: Center(
        child: Text('$name is $age years old'),
      ),
    );
  }
}

// Push with data:
Navigator.push(
  context,
  MaterialPageRoute(
    builder: (c) => DetailScreen(name: 'Chisomo', age: 22),
  ),
);

Simple, type-safe, and works with the Dart compiler to catch errors early.

Returning data — pop with a value

Screens can also send data back. Useful for "pick an option" screens:

// In DetailScreen:
Navigator.pop(context, 'Chisomo');

// In HomeScreen:
final result = await Navigator.push<String>(
  context,
  MaterialPageRoute(builder: (c) => PickerScreen()),
);
print('User picked: $result');

Navigator.pop takes an optional second argument. The await on the caller side waits for it.

Handling the result in a StatefulWidget

void openPicker() async {
  final name = await Navigator.push<String>(
    context,
    MaterialPageRoute(builder: (c) => PickerScreen()),
  );
  if (name != null) {
    setState(() {
      this.name = name;
    });
  }
}

Always check for null — the user might have pressed back without picking anything.

In the sandbox

The sandbox simulates navigation with a simple screen stack. Push screens with Navigator.push(), pop with Navigator.pop(), and pass data via constructor arguments. The result is a working multi-screen app you can test with taps.

Master the pattern of "constructor in, pop value out" and you have 90% of mobile navigation. Everything else — deep linking, nested navigators — builds on it.

Mobile apps rarely live alone. They talk to servers — fetch weather, load posts, sync data. In Flutter, this is done with the http package.

Adding the package

# In pubspec.yaml:
dependencies:
  http: ^1.0.0

Then run flutter pub get. From that point, import 'package:http/http.dart' as http; gives you the client.

A simple GET request

import 'package:http/http.dart' as http;
import 'dart:convert';

Future<void> fetchUser() async {
  final response = await http.get(
    Uri.parse('https://api.example.com/users/1'),
  );

  if (response.statusCode == 200) {
    final data = jsonDecode(response.body);
    print(data['name']);
  } else {
    print('Error: ${response.statusCode}');
  }
}

Four steps:

  1. Build a Uri from the URL string
  2. await the response
  3. Check statusCode — 200 means success
  4. jsonDecode the body (it is JSON text)

Parsing JSON to Dart objects

The clean way: write a class with a factory constructor:

class User {
  final int id;
  final String name;
  final String email;

  User({required this.id, required this.name, required this.email});

  factory User.fromJson(Map<String, dynamic> json) {
    return User(
      id: json['id'],
      name: json['name'],
      email: json['email'],
    );
  }
}

// Usage:
final user = User.fromJson(jsonDecode(response.body));
print(user.name);

fromJson is a factory — a static method that constructs and returns an instance. It is the standard Dart pattern for parsing.

POST with a body

final response = await http.post(
  Uri.parse('https://api.example.com/users'),
  headers: {'Content-Type': 'application/json'},
  body: jsonEncode({
    'name': 'Chisomo',
    'email': 'chisomo@example.mw',
  }),
);

Note the symmetry: jsonDecode for reading, jsonEncode for writing.

Error handling

try {
  final response = await http.get(Uri.parse(url));
  if (response.statusCode != 200) {
    throw Exception('Server returned ${response.statusCode}');
  }
  return jsonDecode(response.body);
} catch (e) {
  print('Request failed: $e');
  rethrow;
}

Networks fail. Always wrap in try/catch and show the user something useful — not a red screen.

In the sandbox, http.get is mocked: it returns realistic JSON after a short delay so you can practise the parsing and loading-state patterns without internet. In a real project, the code is identical — only the URL changes.

Fetching data takes time. Your UI has to handle three states: loading, loaded, and error. Flutter gives you FutureBuilder to make this clean.

The problem without FutureBuilder

You would need a state variable for each of: the data, the loading flag, and the error. Plus an initState to kick off the fetch, and manual setState calls when it completes. Verbose.

FutureBuilder to the rescue

FutureBuilder<List<Post>>(
  future: fetchPosts(),   // a Future
  builder: (context, snapshot) {
    if (snapshot.connectionState == ConnectionState.waiting) {
      return Center(child: CircularProgressIndicator());
    }
    if (snapshot.hasError) {
      return Center(child: Text('Error: ${snapshot.error}'));
    }
    final posts = snapshot.data ?? [];
    return ListView(
      children: posts.map((p) => ListTile(title: Text(p.title))).toList(),
    );
  },
)

Three checks, in order:

  1. waiting — show a spinner
  2. hasError — show the error
  3. otherwise — build the UI with snapshot.data

FutureBuilder handles the state for you. No manual flags.

The Future must be created once

This is the classic Flutter gotcha: if you call fetchPosts() inside build, it re-runs on every rebuild, causing an infinite loop of network requests.

Create the Future once in initState and store it:

class PostsScreen extends StatefulWidget {
  @override
  State<PostsScreen> createState() => _PostsScreenState();
}

class _PostsScreenState extends State<PostsScreen> {
  late Future<List<Post>> futurePosts;

  @override
  void initState() {
    super.initState();
    futurePosts = fetchPosts();   // one call
  }

  @override
  Widget build(BuildContext context) {
    return FutureBuilder<List<Post>>(
      future: futurePosts,
      builder: (context, snapshot) { ... },
    );
  }
}

Now the fetch runs exactly once, and rebuilding only re-runs the builder.

Pull-to-refresh

RefreshIndicator(
  onRefresh: () async {
    setState(() {
      futurePosts = fetchPosts();
    });
    await futurePosts;
  },
  child: ListView(...),
)

Wrap your list in a RefreshIndicator and users can pull down to reload — the standard mobile pattern.

Loading states matter

Show something during the wait — a spinner, a skeleton screen, anything. A blank screen makes the app feel broken. Mobile networks are slower than you think, especially in Malawi; the loading state is not an edge case, it is the normal case.

The three-state pattern — loading, loaded, error — applies to every network call you will ever write. Master it once and reuse it forever.

Structure your project

The default Flutter structure puts everything in lib/main.dart. For real apps, split it:

lib/
├── main.dart
├── models/
│   ├── user.dart
│   └── post.dart
├── screens/
│   ├── home_screen.dart
│   ├── detail_screen.dart
│   └── settings_screen.dart
├── widgets/
│   ├── post_card.dart
│   └── loading_spinner.dart
├── services/
│   └── api_service.dart
└── utils/
    └── constants.dart

Rules of thumb:

  • models — data classes with fromJson
  • screens — one file per screen
  • widgets — reusable UI pieces used by multiple screens
  • services — network calls, storage, anything that talks to the outside world

Extract widgets

When a build method gets longer than ~50 lines, extract a widget. It improves readability and lets Flutter rebuild only what changed:

// Before:
Widget build(BuildContext context) {
  return Column(
    children: [
      Container(
        padding: EdgeInsets.all(16),
        child: Row(
          children: [
            Icon(Icons.person),
            SizedBox(width: 12),
            Text(name),
          ],
        ),
      ),
      // ... 100 more lines
    ],
  );
}

// After:
class UserHeader extends StatelessWidget {
  final String name;
  UserHeader(this.name);

  @override
  Widget build(BuildContext context) {
    return Container(
      padding: EdgeInsets.all(16),
      child: Row(
        children: [
          Icon(Icons.person),
          SizedBox(width: 12),
          Text(name),
        ],
      ),
    );
  }
}

// Now: UserHeader(name)

Const constructors

Mark widgets const when their properties never change. Flutter skips rebuilding them entirely:

const Text('Static label')
const SizedBox(height: 16)
const Icon(Icons.star)

Your IDE will suggest this automatically. Always accept the suggestion — it is a free performance win.

SafeArea

Scaffold(
  body: SafeArea(
    child: Column(...),
  ),
)

SafeArea adds padding for the status bar and notch on modern phones. Without it, your content hides behind the phone's UI chrome.

Theming

Set a global theme once, use it everywhere:

MaterialApp(
  theme: ThemeData(
    primarySwatch: Colors.blue,
    fontFamily: 'Roboto',
    elevatedButtonTheme: ElevatedButtonThemeData(
      style: ElevatedButton.styleFrom(
        padding: EdgeInsets.symmetric(horizontal: 24, vertical: 12),
      ),
    ),
  ),
  home: HomeScreen(),
)

Instead of specifying button styles on every button, set them once. Change the brand color in one place — the whole app updates.

Good Flutter code looks like many small files, each with one clear job. Bad Flutter code looks like one giant main.dart. Aim for the first.

Time to build. The capstone is a weather app: type a city, tap search, fetch weather data, and display it beautifully. Every concept in the course gets used.

What the app does

  • A text input for the city name
  • A search button
  • Shows a loading spinner while fetching
  • Displays the weather: temperature, condition, city
  • Handles errors (unknown city, network failure)

Screen structure

Scaffold
├── AppBar (title: "Weather")
└── body: Padding
    └── Column
        ├── TextField (city input)
        ├── SizedBox(height: 12)
        ├── ElevatedButton (search)
        ├── SizedBox(height: 24)
        └── Result area:
            ├── if loading: CircularProgressIndicator
            ├── if error: Text(error)
            └── if data: WeatherCard

The data model

class Weather {
  final String city;
  final double temperature;
  final String condition;
  final String icon;

  Weather({
    required this.city,
    required this.temperature,
    required this.condition,
    required this.icon,
  });

  factory Weather.fromJson(Map<String, dynamic> json) {
    return Weather(
      city: json['city'],
      temperature: (json['temperature'] as num).toDouble(),
      condition: json['condition'],
      icon: json['icon'],
    );
  }
}

The fetch function

Future<Weather> fetchWeather(String city) async {
  final url = 'https://api.example.com/weather?city=$city';
  final response = await http.get(Uri.parse(url));

  if (response.statusCode != 200) {
    throw Exception('City not found');
  }
  return Weather.fromJson(jsonDecode(response.body));
}

The screen state

You need four pieces of state:

  • city — what the user typed
  • weather — the data when loaded (null while loading)
  • loading — is a request in progress?
  • error — the error message, if any
class _WeatherScreenState extends State<WeatherScreen> {
  final controller = TextEditingController();
  Weather? weather;
  bool loading = false;
  String? error;

  Future<void> search() async {
    setState(() {
      loading = true;
      error = null;
      weather = null;
    });

    try {
      final result = await fetchWeather(controller.text);
      setState(() {
        weather = result;
        loading = false;
      });
    } catch (e) {
      setState(() {
        error = e.toString();
        loading = false;
      });
    }
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: Text('Weather')),
      body: Padding(
        padding: EdgeInsets.all(16),
        child: Column(
          children: [
            TextField(
              controller: controller,
              decoration: InputDecoration(
                labelText: 'City',
                hintText: 'e.g. Lilongwe',
              ),
            ),
            SizedBox(height: 12),
            ElevatedButton(
              onPressed: loading ? null : search,
              child: Text(loading ? 'Searching...' : 'Search'),
            ),
            SizedBox(height: 24),
            if (loading) CircularProgressIndicator(),
            if (error != null) Text('Error: $error'),
            if (weather != null) WeatherCard(weather: weather!),
          ],
        ),
      ),
    );
  }
}

The WeatherCard widget

Extract the display into its own widget — reusable and easier to maintain:

class WeatherCard extends StatelessWidget {
  final Weather weather;
  WeatherCard({required this.weather});

  @override
  Widget build(BuildContext context) {
    return Container(
      padding: EdgeInsets.all(24),
      decoration: BoxDecoration(

      child: Column(

    );
  }

Testing in the sandbox

Type Lilongwe, Blantyre, or Mzuzu to get mock weather. Any other city returns a 404 error. The mock API responds after a delay so you can see the loading state — this is exactly how the real app would behave.

Deploying the real app

  1. Install the Flutter SDK (flutter.dev)
  2. Run flutter create my_weather_app
  3. Replace lib/main.dart with the code from this lesson
  4. Add http to pubspec.yaml and run flutter pub get
  5. Swap the mock URL for a real weather API (OpenWeatherMap has a free tier)
  6. Run flutter run on a connected phone or emulator
  7. Build a release: flutter build apk (Android) or flutter build ios (iOS, needs a Mac)
  8. Publish to Google Play Console or App Store Connect
That's the whole course. You now know Flutter's core: widgets, layout, state, navigation, and APIs. Everything else — Provider, Riverpod, animations, native plugins — is built on these same foundations.
