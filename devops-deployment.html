You can write code. You can build a working project on your laptop. But can you ship it — so that a stranger in Blantyre can open a URL on their phone and use it?

That gap — between "it works on my machine" and "it's live at myname.com" — is where most self-taught developers give up. This course closes it.

What DevOps actually means

DevOps is a set of practices that connect development (writing code) with operations (running it in production). It includes:

  • Version control — Git and GitHub
  • Deployment — getting your code to a server
  • Configuration — environment variables, secrets
  • Networking — domains, DNS, HTTPS
  • Containers — Docker, packaging apps
  • Monitoring — logs, health checks, alerts
  • Recovery — backups, rollbacks, disaster plans

The four moments every project has

  1. Development — you write code on your laptop
  2. Build — code is prepared for production
  3. Deploy — code is sent to a server
  4. Run — users interact with it live

Most tutorials cover step 1 and stop. This course covers 2, 3, and 4.

Why this matters for Malawi

A skilled Malawian developer who can also deploy — reliably, securely, cheaply — is worth far more than one who cannot. Every local business that wants a website, every NGO that needs a data tool, every startup that wants to launch, needs someone who can get code live and keep it running.

And with free tiers from Render, Railway, Fly.io, and Cloudflare, the cost is essentially zero to start.

The promise of this course: by the end, you will have a working project live at a real URL, with a custom domain, HTTPS, environment variables, logging, and a plan for when things break.

Git is the most important tool in a developer's toolkit after the text editor itself. It is not just "save" — it is a complete system for tracking every change you have ever made.

What Git actually does

Git keeps a history of every change to every file in your project. Not just the current state — every state it has ever been in. You can:

  • See what changed between any two points in time
  • Revert to any previous version
  • Work on multiple features simultaneously without conflicts
  • Collaborate with others without overwriting their work
  • Know exactly who changed what, and when

The three areas

Git has three areas:

  1. Working directory — the files you see on disk
  2. Staging area — changes you have marked to include in the next commit
  3. Repository — the permanent history

The workflow is always: edit → add → commit. Edit files, stage the changes you want, commit them with a message.

Why staging matters

Beginners often wonder why they have to "stage" anything. Why not just commit?

Because you do not always want to commit everything. Maybe you fixed a bug AND started an unrelated experiment. You want to commit the fix separately, so the history stays clean.

Staging lets you choose exactly what goes into each commit.

The commands you will use 90% of the time

git status              # what is going on right now?
git add file.txt        # stage one file
git add .               # stage everything
git commit -m "Fix bug" # save the staged changes
git log --oneline       # see recent commits
git diff                # see what changed but is not staged

What a good commit looks like

A commit is a snapshot with a message. Good messages describe why, not what — the diff already shows what changed.

  • Bad: update stuff, fix, asdf
  • Good: Fix login redirect loop when session expires, Add email validation to signup form

Six months from now, when you are debugging a production issue at 11pm, you will thank yourself for the good message.

Try it in the sandbox below The terminal is a real Git simulator. Type help to see available commands. Try this flow:
  • git init
  • echo "Hello" > readme.md
  • git status
  • git add .
  • git commit -m "Add readme"
  • git log --oneline

So far you have committed to a single timeline. But real projects have features, experiments, and fixes happening in parallel. That is what branches are for.

What is a branch?

A branch is a separate line of development. You start from some commit, make changes, and those changes exist only on that branch — until you merge it back.

The default branch is called main (or master in older projects).

Why branches matter

Imagine you are working on a live site. A client asks for a small fix AND a big new feature at the same time.

  • Without branches: you build the feature halfway, then have to ship a broken half-feature to fix the bug.
  • With branches: you make a branch called fix-login-bug, ship the fix, then come back to your feature branch and continue.

The commands

git branch                    # list branches
git branch new-feature        # create a new branch
git checkout new-feature      # switch to it
git checkout -b new-feature   # create and switch, in one step

# ... make changes on the branch ...

git checkout main             # go back to main
git merge new-feature         # merge the branch into main

Fast-forward merges

If main has not changed since you branched off, the merge is trivial. Git just moves the main label forward to point at your branch's latest commit. This is called a fast-forward merge.

If both branches have changes, Git creates a merge commit that combines them — and if the same line of the same file changed on both sides, you have a conflict to resolve.

Merge conflicts

A conflict looks like this in the file:

<<<<<<< HEAD
current change
=======
other change
>>>>>>> other-branch

You edit the file, keep the version you want, delete the markers, then:

git add conflicted-file.txt
git commit

Conflicts are not failures. They are Git saying "you changed this line two ways, please tell me which one wins."

Branching strategy for solo developers

You do not need a complex branching model. For solo work:

  • main is always deployable
  • Every new feature or fix gets its own branch
  • Merge back into main when it works
  • Delete the branch after merging

That is enough. Later, when you join a team, you will learn their specific workflow.

Try branching in the sandbox git checkout -b feature-x then make a commit, then git checkout main, then git merge feature-x. Watch the log.

Git tracks your work locally. GitHub (or GitLab, or Bitbucket) is a remote home for your repository — where your team can see it, and where deployment platforms read from.

Local vs remote

  • Local — the repository on your laptop
  • Remote — a copy on a server (GitHub)

Your local repository knows about remotes. By default, the first remote you add is called origin.

git remote add origin https://github.com/you/repo.git
git push -u origin main

The -u flag sets origin/main as the default upstream, so future git push and git pull know where to go.

The four commands

git clone https://github.com/you/repo.git   # copy a remote repo to your laptop
git pull                                    # fetch + merge remote changes
git push                                    # send local commits to remote
git fetch                                   # download without merging

90% of your time with remotes is pull → work → commit → push.

Pull requests

A pull request (PR) is GitHub's way of proposing changes. You push a branch, then open a PR that says "please review and merge this into main."

Even for solo projects, PRs are useful: they give you a place to review your own work before merging. A quick self-review often catches bugs.

.gitignore

Some files should never be committed. Add a .gitignore file at the root:

# Dependencies
node_modules/
__pycache__/
venv/

# Secrets
.env
.env.local

# OS files
.DS_Store
Thumbs.db

# Build output
dist/
build/
*.log

Rules: never commit node_modules, never commit .env, never commit build output. Anyone can regenerate them.

The one rule about secrets

If you accidentally commit a password, API key, or secret token — assume it is compromised. Changing the commit history does not help; the secret has already been pushed, indexed, and possibly scraped by automated bots that scan GitHub.

The only safe response is:

  1. Rotate the secret immediately (get a new key from the provider)
  2. Delete the old one
  3. Add the file to .gitignore
  4. Commit the fix

GitHub profile README

Create a repository named exactly the same as your GitHub username (e.g. chisomo/chisomo). Put a README.md in it. That README shows on your GitHub profile — it is your front page.

A good profile README is short:

  • One line about what you do
  • Two or three projects pinned
  • Contact links
Treat your GitHub like a portfolio. Recruiters look at it. Commit regularly, write meaningful messages, and pin your best work.

Your code needs secrets: database passwords, API keys, tokens. These must never be hardcoded. Environment variables are the standard way to handle them.

The problem

// NEVER DO THIS
const db = connect({
  host: 'db.example.com',
  password: 'SuperSecret123!',
});

If this code is on GitHub, the password is compromised. If someone steals your laptop, the password is compromised. If a contractor works on the project, they can read the password. And when you need to rotate it — because you will — you have to change code and redeploy.

The solution: environment variables

const db = connect({
  host: process.env.DB_HOST,
  password: process.env.DB_PASSWORD,
});

The values live outside your code. In development, they come from a .env file (which is not committed). In production, they come from the hosting platform's dashboard.

Local development: .env files

# .env — never commit this
DB_HOST=db.example.com
DB_PASSWORD=SuperSecret123!
API_KEY=sk_live_abc123
PORT=3000

Load them with the dotenv package (Node) or python-dotenv (Python):

require('dotenv').config();
// Now process.env.DB_HOST works

Production: the platform's dashboard

Every deployment platform (Render, Railway, Fly.io, Vercel, Netlify) has an "Environment" or "Secrets" section. You paste the same key-value pairs there, and the platform injects them at runtime. The production environment is separate — a stolen dev key does not affect production.

What to store in env vars

  • Database URLs and passwords
  • API keys (Stripe, Anthropic, Twilio, etc.)
  • JWT signing secrets
  • SMTP credentials
  • Sentry / error tracking DSN
  • Feature flags

What NOT to store

  • Non-secret configuration (feature names, timeouts) — those can go in code
  • Anything you would be happy printing in a log

Rotating secrets

You should be able to change any secret without changing code. That is the whole point. A rotation is:

  1. Generate a new key at the provider
  2. Update the value in your dev .env and the platform dashboard
  3. Redeploy (often not even needed for env vars)
  4. Delete the old key at the provider

Do this every 6 months for critical secrets, and immediately if you suspect a leak.

A note on the .env file and Git

If you ever type git status and see .env as an untracked file you might be about to stage — stop. Add it to .gitignore first. Better yet, add it before you create the file.

Practice Open the Env Var Manager in the Tools tab. Add three variables, mark one as secret, and see how the preview output changes.

Time to ship something real. In this lesson you will deploy a Node.js app to a free hosting platform.

The platforms

Three free options that work well from Malawi:

PlatformBest forFree tier
RenderNode, Python, DockerFree web services (spin down after 15 min idle)
RailwayNode, Python, databases$5 free credit/month
Fly.ioAnything, low-latency globalSmall free allowance

For beginners, Render is the most straightforward. Sign up with GitHub, connect a repository, click deploy.

The prep checklist

Before you deploy, make sure your project has:

  1. A package.json with a start script
  2. Environment variables read from process.env
  3. A .gitignore that excludes node_modules and .env
  4. The code pushed to GitHub

package.json

{
  "name": "my-app",
  "version": "1.0.0",
  "scripts": {
    "start": "node server.js",
    "dev": "nodemon server.js"
  },
  "dependencies": {
    "express": "^4.19.2"
  }
}

The platform runs npm install, then npm start. If your start script is wrong, deployment fails.

Respecting the PORT variable

Platforms assign you a port dynamically. Never hardcode it:

const PORT = process.env.PORT || 3000;
app.listen(PORT, () => {
  console.log(`Server running on port ${PORT}`);
});

Locally it runs on 3000. In production, the platform tells your app which port to use.

A minimal server.js

const express = require('express');
const app = express();

app.get('/', (req, res) => {
  res.json({
    message: 'Hello from Malawi',
    time: new Date().toISOString(),
  });
});

const PORT = process.env.PORT || 3000;
app.listen(PORT, () => console.log('Listening on', PORT));

The deployment flow on Render

  1. Push your code to GitHub
  2. Log in to render.com with GitHub
  3. Click "New Web Service"
  4. Select your repository
  5. Set Build Command: npm install
  6. Set Start Command: npm start
  7. Add environment variables under "Environment"
  8. Click "Create Web Service"

First deploy takes 2–3 minutes. You get a URL like my-app.onrender.com. That URL is live.

The free tier reality

Render's free tier spins down apps after 15 minutes of inactivity. The next request takes 30–60 seconds to "wake" the app. This is fine for portfolio projects and demos. For a real production app, pay the $7/month for the always-on tier.

Common failure modes

  • Wrong start script — check package.json
  • Missing env vars — check the dashboard
  • Port hardcoded — use process.env.PORT
  • Node version mismatch — add an "engines" field or a .nvmrc
  • Build failure — read the logs from the dashboard
Deploy early, deploy often. The first deploy of a new project should happen before you have written any real features. It takes 10 minutes and eliminates the "it works locally but not in production" problem forever.

Python is even easier to deploy than Node, since the platform handles the virtual environment for you.

The project structure

my-python-app/
├── app.py
├── requirements.txt
├── .env
├── .gitignore
└── README.md

requirements.txt

The Python equivalent of package.json. It lists dependencies:

Flask==3.0.0
python-dotenv==1.0.0
gunicorn==21.2.0

Generate it with:

pip freeze > requirements.txt

app.py — Flask + production server

from flask import Flask, jsonify
import os

app = Flask(__name__)

@app.route('/')
def home():
    return jsonify({
        'message': 'Hello from Malawi',
        'env': os.environ.get('APP_ENV', 'production'),
    })

if __name__ == '__main__':
    port = int(os.environ.get('PORT', 5000))
    app.run(host='0.0.0.0', port=port)

Why gunicorn

Flask's built-in server is fine for development but not for production. Gunicorn is a production-grade WSGI server that handles concurrency properly.

Your start command becomes:

gunicorn app:app

Read that as: "run the app variable from the app.py module."

Deploying on Render

  1. Push code to GitHub
  2. New Web Service on Render
  3. Build Command: pip install -r requirements.txt
  4. Start Command: gunicorn app:app
  5. Add environment variables
  6. Deploy

That is it. Python deployment is often faster than Node because there is no build step.

Environment variables in Python

import os

DB_URL = os.environ.get('DATABASE_URL')
API_KEY = os.environ.get('API_KEY')

if not DB_URL:
    raise RuntimeError('DATABASE_URL is not set')

The raise pattern is important: fail loudly at startup if a required secret is missing. Do not let the app start with a None value that will crash later in a weird place.

Common failure modes

  • Forgot gunicorn — Flask dev server times out or dies
  • Hardcoded port — must use os.environ.get('PORT')
  • Missing requirements.txt — deploy fails on install step
  • Wrong module path in gunicorn — check that app:app matches your file and variable names

Where to deploy for free

Same platforms as Node: Render, Railway, Fly.io. The setup process is identical — just different build/start commands.

The Python advantage: no build step, no compilation, no bundle size. Python apps go live in less than a minute once the code is on GitHub.

You have a URL like my-app.onrender.com. It works. But you want myname.com — a real domain that you own.

Buying a domain

Registrars sell domains. Common choices:

  • Namecheap — around $10/year for .com
  • Cloudflare Registrar — at-cost, no markup
  • Google Domains — now Squarespace

For a Malawian developer, a .com or a country-specific domain (if you want .mw) works. Prices vary. A .com is the standard choice.

How DNS works

DNS translates a domain name into an IP address. When someone types myname.com:

  1. The browser asks a DNS resolver
  2. The resolver looks up the domain's nameservers
  3. The nameservers tell it the A record (IP address) or CNAME (another domain to look up)
  4. The browser connects to that IP

The records you will set

TypeNameValuePurpose
A@IP addressPoint the root domain
CNAMEwwwmy-app.onrender.comPoint a subdomain
CNAMEapimy-api.onrender.comPoint a subdomain to another service

The @ means the root domain (myname.com). www means www.myname.com.

Connecting your domain to Render

  1. In Render, go to your service → Settings → Custom Domains
  2. Add myname.com and www.myname.com
  3. Render shows you the DNS records to create
  4. Go to your registrar's DNS panel
  5. Add the records as instructed
  6. Wait 5–30 minutes for propagation

DNS changes take time to spread across the internet. It is not instant, but usually under an hour.

HTTPS with Let's Encrypt

HTTPS encrypts traffic between the user and the server. Without it, passwords and data travel in plain text.

Every modern platform provisions HTTPS automatically. Render, Railway, Fly.io, and Netlify all use Let's Encrypt — a free certificate authority — to issue certificates.

Once your domain is connected, HTTPS is enabled automatically. You do not manage certificates. You do not renew them. It just works.

Redirect HTTP to HTTPS

Make sure your site forces HTTPS. On Render, this is on by default. On other platforms, there is usually a "Force HTTPS" toggle.

The www vs root question

You should have one canonical version and redirect the other. Most people pick www (because CNAME records are simpler) or the root (because it is shorter).

On Render: add both as custom domains, and Render redirects automatically to whichever you set as primary.

Verifying

Once connected, open your domain in a browser. You should see:

  • Your app's content
  • A padlock icon (HTTPS)
  • No redirect warnings

If not, check DNS records with dig or the online tool dnschecker.org. Propagation can take up to 24 hours in the worst case.

A domain is worth it. A myname.com looks 100x more professional than a platform subdomain. For a portfolio, for a client, for any serious project — buy the domain. $10/year is nothing compared to the credibility it gives you.

Docker packages your app and everything it needs into a single unit called a container. It runs the same on your laptop, your colleague's laptop, and the server.

The problem Docker solves

"It works on my machine" is the oldest complaint in software. Different OS versions, different Python/Node versions, different system libraries — the same code behaves differently everywhere.

Docker fixes this. You describe the environment once, and it is reproduced exactly wherever the container runs.

Containers vs virtual machines

Traditional virtual machines ship a whole operating system — gigabytes, minutes to boot.

Containers share the host OS kernel. They are megabytes and boot in milliseconds.

A Dockerfile for Node

FROM node:20-alpine

WORKDIR /app

COPY package*.json ./
RUN npm ci --omit=dev

COPY . .

EXPOSE 3000
CMD ["node", "server.js"]

Line by line:

  • FROM — start from a base image (Node 20 on Alpine Linux)
  • WORKDIR — set the working directory inside the container
  • COPY + RUN — install dependencies first (so they cache)
  • COPY . . — copy your code
  • EXPOSE — document which port the app listens on
  • CMD — what runs when the container starts

A Dockerfile for Python

FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 8000
CMD ["gunicorn", "-b", "0.0.0.0:8000", "app:app"]

The three commands

docker build -t my-app .           # build the image
docker run -p 3000:3000 my-app     # run it locally
docker push my-app                 # push to a registry

Once pushed, any server anywhere can pull and run your image.

docker-compose for multi-service apps

When your app needs a database, Redis, or other services:

version: '3'
services:
  web:
    build: .
    ports:
      - "3000:3000"
    environment:
      - DATABASE_URL=postgres://user:pass@db:5432/mydb
    depends_on:
      - db
  db:
    image: postgres:16
    environment:
      - POSTGRES_PASSWORD=pass
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:

Run the whole stack with docker compose up. This is how production systems are typically structured.

When to use Docker (and when to skip it)

Use Docker when:

  • Your app has complex system dependencies
  • You deploy to your own server
  • You have a team and want identical environments
  • You use a platform that expects a Dockerfile

Skip Docker when:

  • You are deploying a simple app to a platform that auto-detects Node/Python
  • You are a solo developer on a small project
  • You are just getting started and Docker is a distraction

Render, Railway, and Vercel all deploy simple apps without any Dockerfile. Use them first. Learn Docker when you outgrow them.

The honest take: Docker is invaluable for teams and complex systems, but for solo projects on modern platforms, it is often unnecessary ceremony. Know what it is, know when to reach for it, and do not add it to a 3-file Express app.

Your app is live. Now what? Once real users are using it, you need to know when things break — and you need a plan for when they do.

Logging: the foundation

Structured logs are the single most useful production tool. Instead of console.log("something happened"), log JSON:

function log(level, message, meta = {}) {
  console.log(JSON.stringify({
    time: new Date().toISOString(),
    level,
    message,
    ...meta,
  }));
}

log('info', 'User signed up', { userId: 42 });
log('error', 'Payment failed', { orderId: 17, reason: 'timeout' });

Why JSON? Because every logging system on the planet can search, filter, and alert on JSON. It is machine-readable.

What to log

  • Every HTTP request: method, path, status, duration
  • Errors with full stack traces and context
  • Business events: signup, purchase, subscription change
  • Slow operations (queries, external API calls)

What NOT to log

  • Passwords (never, ever)
  • Full credit card numbers
  • Authentication tokens
  • Personal data beyond what you need

Health checks

A simple endpoint that reports whether the app is healthy:

app.get('/health', (req, res) => {
  res.json({
    ok: true,
    uptime: process.uptime(),
    version: '1.0.0',
  });
});

Platforms ping this every 30 seconds. If it fails, they alert you.

Error tracking

Sentry (sentry.io) has a generous free tier. It catches unhandled errors and shows you:

  • The exact line of code
  • The user's browser/OS
  • What they did right before
  • How often this error has happened

Setup is one line:

const Sentry = require('@sentry/node');
Sentry.init({ dsn: process.env.SENTRY_DSN });

Backups

Every database needs automatic backups. All managed database providers (Render, Railway, Supabase, Neon) offer daily snapshots. Turn them on.

For files (uploads, images), use object storage (S3, Cloudflare R2, Supabase Storage) rather than the server's local disk. Local disk disappears when the server is redeployed.

The three rules of backups:

  1. Automatic — no one remembers to run manual backups
  2. Tested — you must have restored one to know it works
  3. Off-site — a backup on the same server is not a backup

Graceful shutdown

When the platform restarts your app, it sends SIGTERM first. Handle it to finish in-flight requests:

process.on('SIGTERM', () => {
  console.log('Shutting down gracefully…');
  server.close(() => {
    console.log('Closed out remaining connections');
    process.exit(0);
  });
});

The incident playbook

When something breaks in production:

  1. Stay calm. Panic produces bad decisions.
  2. Check the logs. What was the last error? What changed recently?
  3. Roll back if needed. Platforms keep previous deploys. One click restores them.
  4. Announce it. A short status message in your app or on social media reduces angry messages.
  5. Fix, test, redeploy. Do not fix directly in production — fix in a branch, test, then deploy.
  6. Write a post-mortem. What happened, why, what you will change to prevent it.

The rollback button

On Render, Railway, Vercel, and most platforms, previous deploys are kept. If your latest deploy broke something, click "Rollback" and you are back to the previous version in seconds.

This is why you deploy often: each deploy is small, easy to review, and easy to roll back.
