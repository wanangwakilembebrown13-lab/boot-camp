React is a JavaScript library for building user interfaces. It was created at Facebook in 2013 and is now the most widely used tool for building web apps — used by Instagram, Netflix, Airbnb, and thousands of companies worldwide.

What makes React different?

Traditional websites manipulate the DOM directly. You write document.querySelector and manually change things. As apps grow, this becomes a tangled mess of code that changes the page from a hundred different places.

React flips this: you describe what the UI should look like for a given state, and React figures out how to update the page for you. This is called declarative programming.

Components

In React, you break your UI into small, reusable pieces called components. A button is a component. A navbar is a component. The whole page is a component made of smaller components.

function Welcome() {
  return <h1>Hello, Malawi!</h1>;
}

JSX — HTML inside JavaScript

That strange-looking HTML inside a JavaScript function is called JSX. It's not a string, and it's not valid JavaScript on its own — it's a special syntax that gets compiled into function calls.

Under the hood, Babel turns this:

<h1>Hello</h1>

into this:

React.createElement("h1", null, "Hello")

But you'll never write that. You'll write JSX, and the tools handle the rest.

Your first React app

Every React app has three pieces:

  • React — the core library
  • ReactDOM — renders React into the browser DOM
  • Babel — compiles JSX into JavaScript the browser can run

In the sandbox below, all three are already set up. You just write your component and render it.

React is a library, not a framework. It handles the view layer only. You choose how to add routing, state management, data fetching — unlike Angular or Vue which make those decisions for you.

JSX looks like HTML but has a few important differences. Learning them now saves hours of debugging later.

Rule 1: One parent element

Every component must return a single top-level element. This is wrong:

function App() {
  return (
    <h1>Title</h1>      // ERROR
    <p>Body</p>
  );
}

Wrap them in a <div>, or use a fragment <>...</> which doesn't add an element to the DOM:

function App() {
  return (
    <>
      <h1>Title</h1>
      <p>Body</p>
    </>
  );
}

Rule 2: close every tag

In HTML you can write <img src="...">. In JSX you must self-close: <img src="..." />. Same for <br />, <input />, <hr />.

Rule 3: className, not class

Because class is a reserved word in JavaScript, JSX uses className:

<div className="card">...</div>

Rule 4: { } for expressions

Anywhere inside JSX, { } means "evaluate this JavaScript expression and insert the result":

function App() {
  const name = "Chisomo";
  const skills = ["HTML", "CSS", "JavaScript"];

  return (
    <div>
      <h1>Hello, {name}!</h1>
      <p>2 + 2 = {2 + 2}</p>
      <p>Skills: {skills.join(", ")}</p>
    </div>
  );
}

You can put any valid JavaScript expression inside { } — variables, math, function calls, ternaries. You cannot put statements like if or for.

Rule 5: attributes are camelCase

Most HTML attribute names are the same, but a few are camelCase in JSX:

  • className (not class)
  • htmlFor (not for)
  • onClick (not onclick)
  • onChange (not onchange)

Comments in JSX

{/* This is a JSX comment */}

You can't use // or /* */ directly inside the JSX return — wrap them in { }.

Components are the building blocks of every React app. In modern React, a component is just a JavaScript function that returns JSX.

A function component

function Welcome() {
  return <h1>Hello!</h1>;
}

Two rules:

  1. Name it with a capital letter — Welcome, not welcome. React uses this to tell components apart from regular HTML tags.
  2. It must return JSX (or null).

Using a component

function App() {
  return (
    <div>
      <Welcome />
      <Welcome />
      <Welcome />
    </div>
  );
}

Each <Welcome /> renders an independent copy. This is the whole point — write once, reuse everywhere.

Props — passing data in

Right now the component always says "Hello!" — not very useful. Props let us pass data into a component, like arguments to a function.

function Welcome(props) {
  return <h1>Hello, {props.name}!</h1>;
}

function App() {
  return (
    <div>
      <Welcome name="Chisomo" />
      <Welcome name="Tadala" />
      <Welcome name="Gift" />
    </div>
  );
}

Destructuring — the modern style

You'll almost always see props destructured right in the function signature:

function Welcome({ name, age }) {
  return (
    <div>
      <h1>Hello, {name}!</h1>
      <p>You are {age} years old.</p>
    </div>
  );
}

Props are read-only

Never modify props inside a component. They are the caller's data, not yours:

function Bad({ name }) {
  name = "Hacked";   // DON'T DO THIS
  return <p>{name}</p>;
}
Props flow down the component tree — from parent to child. If a child needs to send data back up, it uses a callback function passed down as a prop. This is the "one-way data flow" that makes React predictable.

Two superpowers that turn your components into real apps: composing them, and rendering lists of them.

Composition with children

Any JSX you put between a component's opening and closing tags becomes a special children prop:

function Card({ title, children }) {
  return (
    <div className="card">
      <h2>{title}</h2>
      <div className="card-body">{children}</div>
    </div>
  );
}

function App() {
  return (
    <Card title="About Me">
      <p>I am learning React.</p>
      <p>I live in Malawi.</p>
    </Card>
  );
}

This is how every layout component works — headers, modals, dialogs, wrappers.

Rendering lists with .map()

You can't write a for loop inside JSX. Instead, use .map() to turn an array of data into an array of JSX elements:

function App() {
  const users = ["Chisomo", "Tadala", "Gift"];

  return (
    <ul>
      {users.map(name => (
        <li key={name}>{name}</li>
      ))}
    </ul>
  );
}

The key prop

Every item in a list must have a unique key. React uses it to track which items changed. Without keys, React warns you and the list can behave unpredictably when items move.

items.map(item => (
  <li key={item.id}>{item.name}</li>
))

Use a stable ID from your data — not the array index (unless the list never reorders).

Conditional rendering

You can't use if inside JSX, but you can use JavaScript expressions:

// Ternary
{isLoggedIn ? <p>Welcome back!</p> : <p>Please log in.</p>}

// Short-circuit AND — render only if condition is true
{items.length > 0 && <p>You have {items.length} items.</p>}

// Or return null from a component
function Message({ show }) {
  if (!show) return null;
  return <p>Hello!</p>;
}
Use && when you only need "show or don't show". Use the ternary ? : when you need two alternative renderings. Reach for if/return null when the logic is more than a line.

Props are read-only. But real apps need to remember things that change — a counter value, form input, whether a menu is open. That's what state is for.

useState — the hook

const [count, setCount] = useState(0);

That single line does a lot:

  • count — the current value
  • setCount — a function to update it
  • useState(0) — the initial value is 0

When you call setCount, React re-renders the component with the new value. This is the fundamental loop of every React app.

Never mutate state directly

This does nothing:

count = count + 1;    // ignored by React

Always call the setter:

setCount(count + 1);  // re-renders

Event handlers

Attach functions to events with camelCase props:

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(count + 1)}>+1</button>
    </div>
  );
}

Notice: onClick receives a function, not a call. Don't write onClick={setCount(count + 1)} — that would call the setter immediately on every render.

The updater function

When the new value depends on the old, use the updater form:

setCount(prev => prev + 1);

This is safer because React batches state updates. If you write setCount(count + 1) twice in a row, both see the same count, and you only get +1. The updater form guarantees you see the latest value.

State is per-component-instance

Each time you render <Counter />, it gets its own independent count. Rendering ten counters gives you ten independent numbers.

React re-renders a component every time its state changes. That's normal — it's how React keeps the UI in sync with the data. Don't fight it; the virtual DOM makes it fast.

Almost every app has a form. In React, forms are handled with controlled components — the input's value is stored in state, and every keystroke updates it.

The pattern

function NameForm() {
  const [name, setName] = useState("");

  return (
    <div>
      <input
        value={name}
        onChange={e => setName(e.target.value)}
        placeholder="Your name"
      />
      <p>Hello, {name || "stranger"}!</p>
    </div>
  );
}

Two things make this controlled:

  • value={name} — the input displays state, not its own internal value
  • onChange — every keystroke calls setName, updating state, which re-renders with the new value

It might feel like extra work compared to plain HTML, but you get full control — you can validate, transform, or reset the input at any time.

Handling form submission

function SignupForm() {
  const [email, setEmail] = useState("");
  const [submitted, setSubmitted] = useState(false);

  function handleSubmit(e) {
    e.preventDefault();       // stop the page reload
    console.log("Submitted:", email);
    setSubmitted(true);
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        type="email"
        value={email}
        onChange={e => setEmail(e.target.value)}
        placeholder="you@example.com"
      />
      <button type="submit">Sign up</button>
      {submitted && <p>Thanks, we got {email}.</p>}
    </form>
  );
}

The e.preventDefault() is critical — without it, the browser tries to submit the form to a server and reloads the page.

Multiple inputs, one state object

When you have several fields, storing them in one state object is cleaner:

const [form, setForm] = useState({ name: "", email: "" });

function handleChange(e) {
  const { name, value } = e.target;
  setForm(prev => ({ ...prev, [name]: value }));
}

<input name="name" value={form.name} onChange={handleChange} />
<input name="email" value={form.email} onChange={handleChange} />

The { ...prev, [name]: value } spread is doing the work: copy everything, then override just the changed field.

Always include a value prop on controlled inputs. If you forget it, React warns you in the console. If you set value but no onChange, the input becomes read-only.

Every React component is a function. The function runs, returns JSX, and finishes. Anything you want to remember between renders has to live in state. But what about side effects — things that touch the outside world?

What is a side effect?

Anything that isn't "return JSX" is a side effect:

  • Setting the document title
  • Fetching data from an API
  • Setting up a timer
  • Adding an event listener to window
  • Writing to localStorage

You can't put these in the render body — they'd run on every single render. That's what useEffect is for.

The signature

useEffect(() => {
  // side effect code here
  return () => {
    // optional cleanup
  };
}, [dependencies]);

The three dependency patterns

No array — runs after every render:

useEffect(() => {
  console.log("Rendered");
});

Empty array — runs once after the first render:

useEffect(() => {
  console.log("Mounted");
}, []);

With dependencies — runs when any of them change:

useEffect(() => {
  document.title = `Count: ${count}`;
}, [count]);

A real example

function Clock() {
  const [time, setTime] = useState(new Date());

  useEffect(() => {
    const id = setInterval(() => setTime(new Date()), 1000);
    return () => clearInterval(id);   // cleanup!
  }, []);

  return <p>{time.toLocaleTimeString()}</p>;
}

Without the cleanup, the interval would keep running even after the component unmounts — a memory leak.

The cleanup function

Whatever you return from useEffect runs:

  • Before the effect runs again (on the next dependency change)
  • When the component unmounts

Use it to cancel timers, abort fetches, remove event listeners — anything that shouldn't outlive the component.

Don't reach for useEffect too quickly. Many things you might think need an effect (like computing a derived value from props) can just be done during render. Use effects for synchronizing with things outside React — that's their job.

Once you've written a few components, you'll notice repeated logic — "get a value from localStorage", "track a counter", "fetch a URL". Custom hooks let you extract that logic and reuse it everywhere.

Rules of hooks

Before writing custom hooks, know the two iron rules:

  1. Only call hooks at the top level of a component or another hook. Never inside loops, conditions, or nested functions.
  2. Only call hooks from React function components or custom hooks — not from plain JavaScript functions.

React relies on hook call order to keep state straight. Break the rules and you get confusing bugs.

A custom hook is just a function

By convention, a custom hook's name starts with use. It can call other hooks. That's the whole idea.

function useCounter(initial = 0) {
  const [count, setCount] = useState(initial);

  const increment = () => setCount(c => c + 1);
  const decrement = () => setCount(c => c - 1);
  const reset = () => setCount(initial);

  return { count, increment, decrement, reset };
}

Now any component can use it:

function Counter() {
  const { count, increment, decrement, reset } = useCounter(10);

  return (
    <div>
      <p>{count}</p>
      <button onClick={increment}>+</button>
      <button onClick={decrement}>-</button>
      <button onClick={reset}>Reset</button>
    </div>
  );
}

A more useful example: useLocalStorage

function useLocalStorage(key, initialValue) {
  const [value, setValue] = useState(() => {
    try {
      const stored = localStorage.getItem(key);
      return stored !== null ? JSON.parse(stored) : initialValue;
    } catch {
      return initialValue;
    }
  });

  useEffect(() => {
    localStorage.setItem(key, JSON.stringify(value));
  }, [key, value]);

  return [value, setValue];
}

Usage:

function Notes() {
  const [notes, setNotes] = useLocalStorage("notes", []);
  // ...
}

The component doesn't know or care that localStorage is involved. The hook hides it.

Why this matters

Custom hooks are the single biggest reason React code scales well. Instead of duplicating fetch logic in five places, you write useUsers() once and import it. When you fix a bug, you fix it in one place.

Custom hooks are the React community's favorite pattern. Every popular library (React Query, React Router, Zustand, etc.) is built on them. Learn to spot repeated logic and extract it.

A traditional website loads a new HTML file for every page. React apps are single-page — the URL changes, but the same HTML file stays loaded, and React swaps out the visible component. This is called client-side routing.

Why client-side routing?

  • Instant navigation — no page reload, no network round trip
  • State persists — the user's login, form data, scroll position all stay
  • Smooth transitions — you can animate between pages

The trade-off: the initial bundle is bigger, and you must handle things like 404 pages yourself.

React Router

The standard router for React is react-router-dom. It provides components that map URLs to components.

import { BrowserRouter, Routes, Route } from "react-router-dom";

function App() {
  return (
    <BrowserRouter>
      <Routes>
        <Route path="/" element={<Home />} />
        <Route path="/about" element={<About />} />
        <Route path="/contact" element={<Contact />} />
      </Routes>
    </BrowserRouter>
  );
}

Three components in play:

  • <BrowserRouter> — wraps the whole app, listens for URL changes
  • <Routes> — looks at the current URL and picks the matching route
  • <Route> — maps a path to a component

Link — for navigation

Never use <a href="/about"> in React. Use <Link> instead:

import { Link } from "react-router-dom";

<nav>
  <Link to="/">Home</Link>
  <Link to="/about">About</Link>
</nav>

<Link> intercepts the click, updates the URL, and lets React re-render — no full page reload. Using a plain <a> would cause a full refresh and lose all your state.

MemoryRouter for the sandbox

In a normal browser you'd use BrowserRouter, which reads the address bar. In the sandbox, we use MemoryRouter instead — it keeps the "URL" in memory only. The API is identical, so everything you learn transfers.

import { MemoryRouter, Routes, Route, Link } from "react-router-dom";

function App() {
  return (
    <MemoryRouter>
      <nav>
        <Link to="/">Home</Link>
        <Link to="/about">About</Link>
      </nav>
      <Routes>
        <Route path="/" element={<Home />} />
        <Route path="/about" element={<About />} />
      </Routes>
    </MemoryRouter>
  );
}
Real projects use BrowserRouter. Sandboxes and tests use MemoryRouter. The rest of your code is identical.

Most apps have pages inside pages: /posts shows a list, /posts/42 shows one post. React Router handles this with URL parameters and nested routes.

URL parameters with useParams

import { useParams } from "react-router-dom";

function PostDetail() {
  const { id } = useParams();
  return <h1>Post #{id}</h1>;
}

<Routes>
  <Route path="/posts/:id" element={<PostDetail />} />
</Routes>

The :id in the path matches any segment. Inside the component, useParams() gives you that value.

Nested routes with Outlet

When you want a shared layout across several child pages:

function Dashboard() {
  return (
    <div>
      <h1>Dashboard</h1>
      <nav>
        <Link to="stats">Stats</Link>
        <Link to="settings">Settings</Link>
      </nav>
      <Outlet />   {/* child route renders here */}
    </div>
  );
}

<Routes>
  <Route path="/dashboard" element={<Dashboard />}>
    <Route path="stats" element={<Stats />} />
    <Route path="settings" element={<Settings />} />
  </Route>
</Routes>

Visiting /dashboard/stats renders Dashboard, then Stats inside the <Outlet />. The header and nav stay mounted — no re-rendering.

Navigating programmatically

Sometimes you need to navigate from code — after a form submits, say:

import { useNavigate } from "react-router-dom";

function LoginForm() {
  const navigate = useNavigate();

  function handleSubmit(e) {
    e.preventDefault();
    // ... authenticate ...
    navigate("/dashboard");
  }

  return <form onSubmit={handleSubmit}>...</form>;
}

NavLink — for active links

<NavLink> is like <Link> but adds an active class when its path matches the current URL:

<NavLink
  to="/about"
  className={({ isActive }) => isActive ? "active" : ""}
>
  About
</NavLink>

Perfect for navbars where the current page should look different.

Nested routes are the single most powerful feature of React Router. Every dashboard, admin panel, and multi-section app is built with them.

No real app is complete without data. Fetching from an API is the most common side effect in React.

The pattern

Fetch data with useEffect, store it in state, handle loading and errors:

function Users() {
  const [users, setUsers] = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    fetch("https://api.example.com/users")
      .then(res => res.json())
      .then(data => {
        setUsers(data);
        setLoading(false);
      })
      .catch(err => {
        setError(err.message);
        setLoading(false);
      });
  }, []);

  if (loading) return <p>Loading…</p>;
  if (error) return <p>Error: {error}</p>;
  return (
    <ul>
      {users.map(u => <li key={u.id}>{u.name}</li>)}
    </ul>
  );
}

Three states to track: the data, whether we're still loading, and whether something went wrong. Every fetch component has these.

Async/await version

Some people find promises with .then() hard to read. The async/await form is flatter:

useEffect(() => {
  async function load() {
    try {
      const res = await fetch("https://api.example.com/users");
      const data = await res.json();
      setUsers(data);
    } catch (err) {
      setError(err.message);
    } finally {
      setLoading(false);
    }
  }
  load();
}, []);

You can't make useEffect's callback itself async — it must return nothing or a cleanup function. So define an inner async function and call it.

Fetching in a custom hook

Extract the pattern so you can reuse it:

function useFetch(url) {
  const [data, setData] = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    let cancelled = false;
    setLoading(true);
    fetch(url)
      .then(r => r.json())
      .then(d => { if (!cancelled) { setData(d); setLoading(false); } })
      .catch(e => { if (!cancelled) { setError(e.message); setLoading(false); } });
    return () => { cancelled = true; };
  }, [url]);

  return { data, loading, error };
}

The cancelled flag prevents setting state on an unmounted component if the user navigates away mid-fetch.

The sandbox mock

In this course, fetch is mocked so you can practice without network access. Three endpoints are available:

  • https://api.example.com/users
  • https://api.example.com/todos
  • https://api.example.com/posts

Each returns realistic JSON after a 500 ms delay — so you can test loading states. In a real project, you'd swap the URL for a real one; the code is identical.

Use one of these patterns every time you fetch: an async function inside useEffect, three states (data, loading, error), and a cancel flag for safety. It's the standard.

Time to build. Over the final two lessons, you'll build a complete Task Manager — add, toggle, delete, and persist to localStorage. Everything you've learned gets used.

What the app does

  • Input to type a new task, plus an Add button
  • A list of tasks, each showing the title and a done checkbox
  • Delete button on each task
  • Filter buttons: All / Active / Done
  • Count of remaining active tasks
  • Persists to localStorage — survives page reload

The data shape

We'll store tasks as an array of objects:

[
  { id: 1, title: "Learn React", done: true },
  { id: 2, title: "Build a project", done: false }
]

Simple, JSON-friendly, easy to filter.

The component plan

  • App — holds the state and handlers
  • TaskForm — input + Add button (receives onAdd prop)
  • TaskItem — one task row (receives task, onToggle, onDelete)
  • TaskList — the list of TaskItems (receives tasks, plus the handlers)
  • FilterBar — the three filter buttons

The rules

  1. State lives in the top-level component. Children receive data as props and events as callbacks.
  2. Never mutate state. Use setTasks(prev => [...]) — always return a new array.
  3. Every task item has a stable key. We'll use the task's id.

Persisting to localStorage

Use the custom hook pattern from lesson hk2:

const [tasks, setTasks] = useLocalStorage("react-tasks", []);

Every time tasks changes, the hook writes it to localStorage. On page load, it reads the stored value — so the user's tasks come back.

Adding a task

function addTask(title) {
  setTasks(prev => [
    ...prev,
    { id: Date.now(), title, done: false }
  ]);
}

Date.now() gives us a unique id for free. Not perfectly safe in theory, but fine for a local app.

Toggling done

function toggleTask(id) {
  setTasks(prev =>
    prev.map(t =>
      t.id === id ? { ...t, done: !t.done } : t
    )
  );
}

The .map returns a new array, and each task is either copied with a flipped done or kept as-is. React sees a new array, re-renders, and the UI updates.

Deleting

function deleteTask(id) {
  setTasks(prev => prev.filter(t => t.id !== id));
}

Filtering

The filter is UI state, not data state — it doesn't need to persist:

const [filter, setFilter] = useState("all");

const visible = tasks.filter(t => {
  if (filter === "active") return !t.done;
  if (filter === "done") return t.done;
  return true;
});
That's the whole app. Every feature you've learned — components, props, useState, useEffect, custom hooks — gets used. When you finish, you have a real portfolio piece.
