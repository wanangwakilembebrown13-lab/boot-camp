Every Malawian business that wants to sell online needs a way to accept payment. And in Malawi, that almost always means mobile money — Airtel Money or TNM Mpamba.

Learning to integrate these APIs makes you immediately valuable. Every e-commerce shop, ticketing platform, school fee system, and subscription service in the country needs exactly this, and almost no developer can build it.

What is mobile money?

Mobile money is a payment system where the "account" is a phone number, and the balance is held by the mobile network operator (MNO). Users can:

  • Send money to another phone number
  • Pay merchants and bills
  • Withdraw cash at agents
  • Receive remittances

The two dominant providers in Malawi are Airtel Money (Airtel Malawi) and TNM Mpamba (Telekom Networks Malawi). Together they reach nearly every adult with a phone.

Why this matters for developers

If you are building any of these, you need mobile money:

  • E-commerce checkout for an online shop
  • Ticket sales (concerts, sports, events)
  • School or university fee payments
  • Subscriptions (streaming, news, membership)
  • Donations for NGOs and churches
  • Delivery payments for food and groceries

Every one of these businesses is currently paying someone — often a foreign agency — to integrate mobile money. A Malawian developer who can do this locally has an instant advantage.

The two sides

Every mobile money integration has two directions:

  1. Collections — you receive money from a customer (checkout, subscriptions, donations)
  2. Disbursements — you send money to someone (refunds, payouts, salaries, dividends)

Most businesses start with collections and add disbursements later.

The mental model

Think of the payment flow as four steps:

  1. Your server tells the API "I want to charge customer X K5,000"
  2. The API sends a prompt to the customer's phone (a "push")
  3. The customer enters their PIN on their phone to approve
  4. The API sends a webhook back to your server saying "payment succeeded" or "payment failed"

Your code must handle all four. The customer's phone is the source of truth, not your server — this is the single most important thing to understand.

Try the simulator Scroll to the sandbox. Pick a provider (Airtel or TNM), click "Charge customer," and watch the full flow: request out, phone prompt, customer approval, webhook back. This is exactly what happens in production.

Both Airtel Money and TNM Mpamba offer developer APIs. The pattern is similar across both, but the details differ. This lesson gives you the conceptual shape.

Authentication

Every API request must be authenticated. Both providers use OAuth 2.0:

  1. Your server sends a client_id and client_secret to the auth endpoint
  2. The provider returns an access token (valid for ~1 hour)
  3. Every subsequent request includes Authorization: Bearer <token>
POST /auth/oauth2/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
&client_id=YOUR_CLIENT_ID
&client_secret=YOUR_CLIENT_SECRET

Response:

{
  "access_token": "eyJhbGciOi...",
  "token_type": "Bearer",
  "expires_in": 3600
}

Cache the token and refresh it when it expires. Do not fetch a new one for every request — that is slow and rate-limited.

The webhook

When the customer approves or rejects the prompt, the provider sends a POST to a URL you registered:

POST https://yourapp.com/webhooks/mobile-money
Content-Type: application/json

{
  "transaction": {
    "id": "TX-abc-123",
    "status": "TS",       // TS = success, TF = failed, TP = pending
    "amount": 5000,
    "currency": "MWK"
  },
  "reference": "ORDER-12345"
}

Your server must:

  1. Verify the webhook (signature or IP allowlist)
  2. Look up the order by reference
  3. Mark it as paid (or failed)
  4. Respond 200 OK quickly (within 5 seconds)

Testing vs production

Both providers offer a sandbox — a fake environment where no real money moves. Use it exclusively until you have a signed merchant agreement.

  • Sandbox base URL — usually https://openapi.airtel.africa/sandbox/ or similar
  • Production base URL — different domain, requires approval
  • Same code — only the base URL and credentials change
Practice In the sandbox, try both providers. Notice the endpoints and payloads are nearly identical, just different credentials and status codes.

Let's walk through a complete collection flow, from the moment your customer clicks "Pay" to the moment their order is confirmed.

Step 1 — Customer clicks "Pay"

Your frontend sends a request to your own backend (not directly to the API — your client secret never leaves the server):

POST https://yourapp.com/api/checkout
{
  "orderId": "ORDER-12345",
  "amount": 5000,
  "currency": "MWK",
  "phone": "265991234567",
  "provider": "airtel_money"
}

Step 2 — Backend initiates the charge

async function initiateCharge(orderId, phone, amount) {
  const token = await getAccessToken();

  const response = await fetch(
    'https://openapi.airtel.africa/merchant/v1/payments/',
    {
      method: 'POST',
      headers: {
        'Authorization': 'Bearer ' + token,
        'Content-Type': 'application/json',
        'X-Country': 'MW',
        'X-Currency': 'MWK',
      },
      body: JSON.stringify({
        reference: orderId,
        subscriber: {
          country: 'MW',
          currency: 'MWK',
          msisdn: phone,
        },
        transaction: {
          amount: amount,
          country: 'MW',
          currency: 'MWK',
          id: generateTransactionId(),
        },
      }),
    }
  );

  return response.json();
}

The response comes back in under a second. It says "we received your request, we are pushing to the phone." It does NOT say the payment succeeded.

Step 3 — Customer sees the prompt

On their phone, the customer sees something like:

Airtel Money
A payment request of MWK 5,000 from TechMountain Store is waiting.
Enter your PIN to approve.
Ref: ORDER-12345

They have 60 seconds to enter their PIN. If they do, payment succeeds. If they do not, or they cancel, payment fails. If they have insufficient balance, it fails.

Step 4 — Webhook arrives

While the customer is deciding, your server is waiting. When they approve or reject, the provider POSTs to your webhook URL:

app.post('/webhooks/mobile-money', async (req, res) => {
  // 1. Immediately acknowledge
  res.status(200).send('OK');

  // 2. Then process asynchronously
  try {
    const { reference, transaction } = req.body;

    if (transaction.status === 'TS') {
      await markOrderPaid(reference, transaction.id);
    } else if (transaction.status === 'TF') {
      await markOrderFailed(reference, transaction.id);
    }
    // 'TP' means still pending — wait for a second webhook
  } catch (err) {
    console.error('Webhook processing failed:', err);
  }
});

Notice two things:

  1. Respond 200 immediately. The provider retries if you take too long, which can cause duplicate webhooks.
  2. Process asynchronously. Do the actual work (marking the order, sending confirmation emails) after you have acknowledged receipt.

Step 5 — Frontend polls for status

The customer does not know what your webhook received. Their browser needs to know when the order is confirmed:

async function pollOrderStatus(orderId) {
  while (true) {
    const res = await fetch('/api/orders/' + orderId);
    const data = await res.json();

    if (data.status === 'paid') return 'success';
    if (data.status === 'failed') return 'failed';

    await sleep(2000); // check every 2 seconds
  }
}

Alternatively, use Server-Sent Events or WebSockets for instant updates. For most small shops, polling every 2 seconds is fine.

The 60-second window

Between step 2 and step 4, there is a gap. During this gap:

  • The order is in a pending state
  • The customer sees "waiting for approval" on the screen
  • If the webhook never comes (network failure), you need a timeout: after 90 seconds, mark the order as failed_timeout

Common failure modes

  • Customer cancels the prompt — status TF
  • Customer enters wrong PIN three times — status TF
  • Insufficient balance — status TF
  • Phone not registered for mobile money — status TF
  • Number is wrong format — API rejects immediately
  • Webhook lost — no webhook arrives; use a status-check endpoint after 90 seconds as a fallback
The core principle: the webhook is the source of truth. Your server initiates; the customer approves on their phone; the webhook tells you the result. Never trust a client-side "success" message.

You can also send money the other way — from your merchant account to a customer's phone. This is how refunds, payouts, and salary distributions work.

When to use disbursements

  • Refunds — customer returns a product, you send money back
  • Marketplace payouts — sellers on your platform get their share
  • Salary or dividend payments — pay staff or investors
  • Referral commissions — pay users who refer others
  • Cashback or loyalty rewards

The endpoint

POST /merchant/v1/payments/disburse
Authorization: Bearer <token>

{
  "reference": "REFUND-12345",
  "subscriber": {
    "country": "MW",
    "currency": "MWK",
    "msisdn": "265991234567"
  },
  "transaction": {
    "amount": 2500,
    "country": "MW",
    "currency": "MWK",
    "id": "PAYOUT-xyz"
  }
}

The customer does not need to approve anything. Money arrives directly in their mobile money account within seconds.

The float requirement

To send money out, your merchant account needs float — a balance of money that the provider holds for you. If your float runs out, disbursements fail.

Typical setup:

  1. You deposit money into your merchant account (via bank transfer)
  2. The provider credits your float
  3. You can disburse up to your float balance
  4. Top up whenever it runs low

This is why most businesses start with collections and only add disbursements once they have revenue coming in.

Reconciliation matters

Every disbursement costs money and moves real funds. You need to know exactly:

  • How much you have sent today
  • Which transactions succeeded
  • Which are pending
  • Your remaining float balance

Log every disbursement to your database, with the reference, amount, status, and the provider's transaction ID.

Building a payout system

async function sendPayout(recipientPhone, amount, reason) {
  const reference = 'PAYOUT-' + Date.now();

  // 1. Record it as pending BEFORE sending
  await db.insert('payouts', {
    reference,
    phone: recipientPhone,
    amount,
    status: 'initiating',
    reason,
  });

  // 2. Call the API
  try {
    const result = await airtelAPI.disburse({
      reference,
      phone: recipientPhone,
      amount,
    });

    // 3. Update status
    await db.update('payouts', reference, {
      status: 'pending',
      providerTxId: result.transaction.id,
    });
  } catch (err) {
    await db.update('payouts', reference, {
      status: 'failed',
      error: err.message,
    });
    throw err;
  }
}

Notice: record before sending. If the API call succeeds but your server crashes before recording, you have a payment you cannot explain.

Webhook for disbursements

Disbursements also send webhooks — with the same status codes (TS, TF, TP). Handle them the same way:

app.post('/webhooks/mobile-money', async (req, res) => {
  res.status(200).send('OK');
  const { reference, transaction } = req.body;

  // Find the payout record
  const payout = await db.findByReference(reference);
  if (!payout) return; // not ours

  if (transaction.status === 'TS') {
    await db.updatePayout(reference, { status: 'paid' });
  } else if (transaction.status === 'TF') {
    await db.updatePayout(reference, { status: 'failed' });
  }
});

Safety rules

  • Never disburse to a number that has not been verified. A typo sends money to a stranger.
  • Log every disbursement in your database first. The API call is secondary.
  • Rate-limit. A bug that fires 1,000 payouts per minute will drain your float instantly.
  • Two-person rule for large amounts. Above some threshold, require a second approval.
  • Never trust user input for the phone number. Verify it via an OTP first.
Collections and disbursements are not symmetric. Sending money out is a hundred times riskier than receiving it — a bug that double-sends is money you cannot get back. Treat disbursement code with extreme care.

Webhooks are the backbone of any payment integration. Handled correctly, they make your system reliable. Handled naively, they cause duplicates, lost payments, and angry customers.

What is a webhook?

Instead of your server asking "did the payment succeed yet?" a hundred times, the provider pushes the result to you. That push is a webhook — an HTTP POST to a URL you registered.

Your webhook URL must be

  • Publicly accessible — the provider needs to reach it
  • HTTPS — the provider will not send to HTTP
  • Fast — responds 200 within 5 seconds
  • Idempotent — see lesson m6

A production-grade webhook handler

const express = require('express');
const app = express();

app.post('/webhooks/mobile-money',
  express.json({ limit: '100kb' }),
  async (req, res) => {
    // 1. Verify the source
    if (!verifyWebhookSignature(req)) {
      return res.status(401).send('Unauthorized');
    }

    // 2. Acknowledge immediately
    res.status(200).send('OK');

    // 3. Process asynchronously
    try {
      await processWebhook(req.body);
    } catch (err) {
      console.error('Webhook processing failed:', err);
      // Do NOT return an error — you already sent 200.
      // Log it, and rely on reconciliation to catch it.
    }
  }
);

Three critical decisions:

  1. Verify the signature. Anyone can POST to your endpoint. Verify the HMAC signature or IP allowlist before trusting the payload.
  2. Respond 200 first. Providers retry if you are slow. Retries create duplicates.
  3. Process after responding. Your handler runs after the 200, so slow processing does not cause retries.

Why respond 200 first?

Because you cannot know if processing will succeed. If your database is momentarily unavailable, and you return 500, the provider retries — and you now have two deliveries of the same event. If you already processed the first one successfully, you now double-charge the customer.

Instead: acknowledge receipt, then process. If processing fails, log it, and reconciliation will catch it later.

Verifying webhook signatures

Most providers sign webhooks with an HMAC of the payload using a secret only you and they know:

const crypto = require('crypto');

function verifyWebhookSignature(req) {
  const signature = req.headers['x-signature'];
  const secret = process.env.WEBHOOK_SECRET;

  const expected = crypto
    .createHmac('sha256', secret)
    .update(JSON.stringify(req.body))
    .digest('hex');

  return crypto.timingSafeEqual(
    Buffer.from(signature),
    Buffer.from(expected)
  );
}

Two important details:

  • timingSafeEqual — a naive string compare leaks information via timing.
  • Read the raw body. Some frameworks parse the body and change its formatting, breaking the signature. Use a raw-body middleware for webhook routes.

What if the webhook never arrives?

Webhooks can be lost — network failure, provider outage, deploy in progress. Always have a fallback:

  1. After initiating a payment, schedule a status check for 90 seconds later
  2. The status check calls the provider's query endpoint (every provider has one)
  3. If the transaction is successful but you never received the webhook, mark the order as paid
setTimeout(async () => {
  const order = await db.getOrder(reference);
  if (order.status !== 'paid') {
    const status = await provider.queryTransaction(order.providerTxId);
    if (status === 'TS') {
      await markOrderPaid(reference);
    }
  }
}, 90000);

This single pattern eliminates 99% of "lost webhook" problems.

The retry storm

During a provider outage, they may retry the same webhook for hours. If your handler is not idempotent, you will process the same payment dozens of times.

Two mitigations:

  1. Idempotency key (lesson m6) — ignore duplicate events by transaction ID
  2. Fast responses — the faster you respond 200, the less they retry
The webhook contract: acknowledge immediately, verify the source, process asynchronously, handle duplicates, and have a polling fallback. Do all five and your payment system will be reliable. Skip any one and you will have incidents.

Idempotency is the property that doing the same operation twice has the same effect as doing it once. For payments, it is not optional — it is the difference between charging a customer once and charging them five times.

The duplicate problem

Duplicates come from everywhere:

  • The provider retries a webhook because your response was slow
  • The customer double-clicks "Pay"
  • Your server times out and retries internally
  • You replay a webhook while debugging
  • A network blip causes the same request to be delivered twice

Without idempotency, each of these creates a duplicate charge.

The idempotency key

The solution is a unique key that identifies the operation. The second time you see the same key, you return the cached result instead of doing the work again.

For a payment, the key is usually the transaction ID from the provider.

async function processWebhook(payload) {
  const txId = payload.transaction.id;

  // Check if we have already processed this transaction
  const existing = await db.findOne('processed_transactions', {
    providerTxId: txId,
  });

  if (existing) {
    console.log('Duplicate webhook, ignoring:', txId);
    return existing.result;
  }

  // First time — do the work
  const result = await markOrderPaid(payload.reference, txId);

  // Record that we did it
  await db.insert('processed_transactions', {
    providerTxId: txId,
    processedAt: new Date(),
    result: 'success',
  });

  return result;
}

The processed_transactions table (or unique constraint on the column) is what makes this work. The second call sees the first call's record and skips the work.

The unique constraint approach

Even better than a check-then-insert is a database unique constraint:

CREATE TABLE processed_transactions (
  provider_tx_id TEXT PRIMARY KEY,
  order_reference TEXT NOT NULL,
  processed_at TIMESTAMPTZ DEFAULT NOW()
);

Now if two webhook handlers run simultaneously for the same transaction, one wins and the other gets a constraint violation — which you catch and treat as "already processed."

Idempotency for outgoing requests

When you initiate a payment, use the same principle. Send an idempotency key with the request:

POST /merchant/v1/payments/
Idempotency-Key: ORDER-12345-initiate

{
  "reference": "ORDER-12345",
  "transaction": { ... }
}

If the request times out and you retry with the same key, the provider will not initiate a second charge. They will return the result of the first.

Timeouts and retries

The rule for retrying:

  • Retry on network errors, timeouts, and 5xx responses — but only with an idempotency key
  • Do not retry on 4xx responses (except 429)
  • Use exponential backoff — wait 1s, then 2s, then 4s, then 8s. Do not hammer the API.
async function retry(fn, attempts = 5) {
  for (let i = 0; i < attempts; i++) {
    try {
      return await fn();
    } catch (err) {
      if (!isRetryable(err) || i === attempts - 1) throw err;
      await sleep(Math.pow(2, i) * 1000);
    }
  }
}

The ledger

Every payment integration needs a ledger — an append-only record of every transaction, with its full lifecycle:

{
  id: 'uuid',
  reference: 'ORDER-12345',
  provider: 'airtel_money',
  providerTxId: 'TX-abc-123',
  amount: 5000,
  currency: 'MWK',
  status: 'success',
  customerPhone: '265991234567',
  createdAt: '2025-06-12T14:32:01Z',
  completedAt: '2025-06-12T14:32:47Z',
  rawWebhooks: [...]
}

The ledger is your source of truth when something goes wrong. When a customer says "I paid but did not get my order," you look up the reference and see exactly what happened.

The principle: treat every payment operation as if it will be attempted twice. Design for the duplicate from the start, and you will never wake up to a customer who was charged five times.

Reconciliation is the daily process of comparing your records against the provider's records and fixing any differences. It is boring. It is also essential.

Why reconciliation matters

Discrepancies happen even with good code:

  • A webhook was lost and your order stayed "pending"
  • A webhook arrived twice and you accidentally double-counted
  • A payment succeeded but was marked failed by a bug
  • A refund went out but was never recorded
  • A customer was charged but their order was never created

Without reconciliation, these errors sit in your database forever. With reconciliation, you catch them the next morning.

What the provider gives you

Both Airtel and TNM offer a transaction history API — a list of every transaction for your merchant account for a given day or date range:

GET /merchant/v1/transactions/?date=2025-06-12

{
  "transactions": [
    {
      "id": "TX-abc-123",
      "reference": "ORDER-12345",
      "amount": 5000,
      "status": "TS",
      "time": "2025-06-12T14:32:47Z"
    },
    ...
  ]
}

The reconciliation script

Run it every night at midnight (or every morning at 6am). It compares the two datasets and reports discrepancies.

async function reconcile(date) {
  // 1. Fetch provider transactions for the day
  const providerTxs = await provider.getTransactions(date);

  // 2. Fetch your transactions for the same day
  const ourTxs = await db.getTransactions(date);

  // 3. Build lookup maps by provider transaction ID
  const providerMap = new Map();
  providerTxs.forEach(tx => providerMap.set(tx.id, tx));

  const ourMap = new Map();
  ourTxs.forEach(tx => ourMap.set(tx.providerTxId, tx));

  const discrepancies = [];

  // 4. Provider has it, we do not — we missed a transaction
  for (const [txId, tx] of providerMap) {
    if (!ourMap.has(txId)) {
      discrepancies.push({
        type: 'missing_on_our_side',
        txId,
        reference: tx.reference,
        amount: tx.amount,
      });
    }
  }

  // 5. We have it, provider does not — we have a phantom transaction
  for (const [txId, tx] of ourMap) {
    if (!providerMap.has(txId)) {
      discrepancies.push({
        type: 'missing_on_provider_side',
        txId,
        reference: tx.reference,
      });
    }
  }

  // 6. Status mismatch — we said success, they say failed
  for (const [txId, ourTx] of ourMap) {
    const providerTx = providerMap.get(txId);
    if (providerTx && ourTx.status !== mapStatus(providerTx.status)) {
      discrepancies.push({
        type: 'status_mismatch',
        txId,
        ours: ourTx.status,
        theirs: providerTx.status,
      });
    }
  }

  // 7. Report
  if (discrepancies.length) {
    await sendAlert('Reconciliation discrepancies', discrepancies);
  }

  return discrepancies;
}

Handling each type of discrepancy

TypeAction
Missing on our sideCreate the transaction record and, if it was a payment, fulfil the order
Missing on provider sideInvestigate — was this a duplicate insert? A test transaction? Mark as suspect
Status mismatchTrust the provider. Update our record.

The daily report

Every morning, send yourself an email or Slack message with:

  • Total collections (amount, count)
  • Total disbursements (amount, count)
  • Current float balance
  • Number of discrepancies and their details

This takes two minutes to read and catches every problem before your customers complain.

Monthly bank reconciliation

Once a month, compare the total amount the provider says you received against what actually hit your bank account. Small discrepancies (rounding, fees) are normal. Large ones are not.

The discipline: payments is one of the few areas where "it works in testing" is not enough. You need a system that catches its own mistakes, because they will happen. Reconciliation is that system.

You have the backend working. Now for the part your customer actually sees — the checkout page.

The checkout page's job

A good checkout page:

  • Shows the amount clearly (in MWK, with no hidden fees)
  • Asks for the phone number (or remembers it if the user is logged in)
  • Lets the customer pick their provider (Airtel or TNM)
  • Has one obvious button: "Pay K5,000"
  • Shows a clear waiting state with the amount and a countdown
  • Shows a clear success or failure state with a next step

The three states

Your checkout UI has three screens:

  1. Form — collect phone number and provider
  2. Waiting — "Check your phone, enter your PIN"
  3. Result — success (with order confirmation) or failure (with retry)

Do not skip any of these. A page that goes straight from form to success is lying to the customer.

The frontend logic

async function pay() {
  const phone = document.getElementById('phone').value;
  const provider = document.querySelector('.providers button.selected').dataset.provider;

  showState('waiting');
  document.getElementById('waiting-phone').textContent = phone;

  // 1. Ask our backend to initiate the charge
  const res = await fetch('/api/checkout', {

  const result = await pollUntilFinal(oid, { intervalMs: 2000, timeoutMs: 90000 });

  if (result.status === 'paid') {
    showState('success');
  } else {
    document.getElementById('failure-reason').textContent = result.reason;
    showState('failure');
  }
}

Mobile-first considerations

Most of your customers will use your checkout on a phone. That means:

  • Big buttons — thumb-sized, at least 44px tall
  • Number keyboard — type="tel" for the phone input
  • No unnecessary steps — the customer is already on the phone they will pay from
  • Clear error messages — "This number is not registered for Airtel Money" not just "Error"
  • Fast — mobile checkouts should be under 50 KB and load in 2 seconds (see the Low Bandwidth course)

Prefill whenever possible

If the customer is logged in, prefill their phone number from their profile. If they have paid with Airtel before, default to Airtel. Reduce friction and you reduce drop-off.

Trust signals

Payments require trust. Add:

  • The business name clearly displayed
  • The exact amount, no surprises
  • A visible "secured by Airtel Money" or "TNM Mpamba" badge
  • A support phone number or WhatsApp link
  • A link to refund policy

The cancel button matters

If a customer cannot cancel, they panic. Give them a clear "Cancel" button. When they cancel, stop polling and show a "Payment cancelled" state. Whether the provider's prompt still succeeds is not your problem — if it does, you will see it via webhook and can handle it.

Every second of friction loses customers. The best mobile money checkout in Malawi has three fields and one button. Aim for that.

Payment systems are the highest-value target for attackers. If you build one, you must handle security like a professional.

The credentials you must protect

  • Client ID and client secret — used to authenticate with the provider
  • Webhook secret — used to verify incoming webhooks
  • API keys — for querying transaction status

These never go in source code. Never. Not in a comment saying "TODO: move this." Not in a test file. Not in a commit that you plan to revert later.

Environment variables only

const AIRTEL_CLIENT_ID = process.env.AIRTEL_CLIENT_ID;
const AIRTEL_CLIENT_SECRET = process.env.AIRTEL_CLIENT_SECRET;
const WEBHOOK_SECRET = process.env.WEBHOOK_SECRET;

if (!AIRTEL_CLIENT_ID || !AIRTEL_CLIENT_SECRET) {
  throw new Error('Airtel credentials missing. Check env vars.');
}

The throw at startup is critical: if a required secret is missing, fail immediately with a clear message. Do not start and then crash unpredictably in the middle of a payment.

Never log

  • Client secrets
  • Webhook signatures
  • Customer PINs (you never see these anyway — good)
  • Full phone numbers in production logs
  • The raw body of webhook requests containing sensitive data

Redact sensitive data

If you must log transaction details, redact:

function redact(value, keep = 4) {
  if (!value) return value;
  const s = String(value);
  return '***' + s.slice(-keep);
}

logger.info('Processing payment', {
  reference: order.reference,
  amount: order.amount,
  phone: redact(order.phone, 4),  // ***4567
});

Verify every webhook

Anyone on the internet can POST to your webhook URL. Without verification, an attacker can mark orders as paid without paying.

Two ways to verify:

  1. HMAC signature — the provider includes a signature header, computed with a shared secret
  2. IP allowlist — only accept requests from the provider's published IP ranges

Use both if you can. At minimum, use one.

Always query after a webhook

Even after verifying the signature, query the provider to confirm the transaction:

async function processWebhook(payload) {
  // Trust but verify
  const verified = await provider.queryTransaction(payload.transaction.id);

  if (verified.status !== 'TS') {
    console.warn('Webhook said success but query says:', verified.status);
    return;
  }

  await markOrderPaid(payload.reference);
}

This costs one extra API call per payment and eliminates the entire class of forged-webhook attacks.

Rate limiting

Add rate limits to every endpoint that touches payments:

const rateLimit = require('express-rate-limit');

app.use('/api/checkout', rateLimit({
  windowMs: 60 * 1000,       // 1 minute
  max: 5,                    // 5 requests per IP per minute
}));

app.use('/webhooks/mobile-money', rateLimit({
  windowMs: 60 * 1000,
  max: 100,                  // providers may retry quickly
}));

HTTPS everywhere

Payment endpoints must be HTTPS. No exceptions. If your platform does not provide HTTPS automatically, set it up with Let's Encrypt (see the DevOps course).

The PIN is sacred

You never see the customer's PIN — the provider handles it on their phone. If anyone ever asks you to collect a PIN, it is a scam. Your code should never need it.

Never store card data

Mobile money does not use card numbers, but if you ever add card payments, use a provider like Stripe or Paystack who handles the card data for you. Never store card numbers on your own server.

Provider client (provider.js)

const fetch = require('node-fetch');

let cachedToken = null;
let tokenExpiresAt = 0;

async function getToken() {
  if (cachedToken && Date.now() < tokenExpiresAt - 60000) {
    return cachedToken;
  }
  const res = await fetch(process.env.PROVIDER_AUTH_URL, {
    method: 'POST',
    headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
    body: new URLSearchParams({
      grant_type: 'client_credentials',
      client_id: process.env.PROVIDER_CLIENT_ID,
      client_secret: process.env.PROVIDER_CLIENT_SECRET,
    }),
  });
  const data = await res.json();
  cachedToken = data.access_token;
  tokenExpiresAt = Date.now() + data.expires_in * 1000;
  return cachedToken;
}

async function initiateCharge(order) {
  const token = await getToken();
  const res = await fetch(process.env.PROVIDER_PAYMENTS_URL, {
    method: 'POST',
    headers: {
      'Authorization': 'Bearer ' + token,
      'Content-Type': 'application/json',
      'X-Country': 'MW',
      'X-Currency': 'MWK',
      'Idempotency-Key': order.reference + '-initiate',
    },
    body: JSON.stringify({
      reference: order.reference,
      subscriber: { country: 'MW', currency: 'MWK', msisdn: order.phone },
      transaction: {
        amount: order.amount,
        country: 'MW',
        currency: 'MWK',
        id: order.providerTxId,
      },
    }),
  });
  return res.json();
}

async function queryTransaction(providerTxId) {
  const token = await getToken();
  const res = await fetch(
    process.env.PROVIDER_QUERY_URL + '?id=' + providerTxId,
    { headers: { 'Authorization': 'Bearer ' + token } }
  );
  return res.json();
}

module.exports = { getToken, initiateCharge, queryTransaction };

Order model with safe state transitions (orders.js)

const ALLOWED = {
  pending: ['paid', 'failed', 'failed_timeout'],
  paid: [],
  failed: [],
  failed_timeout: [],
};

async function transition(orderId, newStatus) {
  const order = await db.getOrder(orderId);
  if (!ALLOWED[order.status].includes(newStatus)) {
    throw new Error(`Invalid transition: ${order.status} -> ${newStatus}`);
  }
  await db.update('orders', orderId, {
    status: newStatus,
    [`${newStatus}At`]: new Date(),
  });
}

module.exports = { transition };

The state machine is critical. It prevents bugs like marking a failed order as paid twice, or a paid order as failed after the fact.

Webhook handler with all the safeguards (webhooks.js)

const express = require('express');
const crypto = require('crypto');
const provider = require('./provider');
const orders = require('./orders');

const router = express.Router();

router.post('/webhooks/mobile-money',
  express.raw({ type: 'application/json' }),
  async (req, res) => {

    // 1. Respond immediately
    res.status(200).send('OK');

    // 2. Verify signature
    const signature = req.headers['x-signature'];
    const expected = crypto
      .createHmac('sha256', process.env.WEBHOOK_SECRET)
      .update(req.body)
      .digest('hex');

    if (!signature || !crypto.timingSafeEqual(
      Buffer.from(signature), Buffer.from(expected)
    )) {
      console.warn('Webhook signature invalid, ignoring');
      return;
    }

    // 3. Parse
    const payload = JSON.parse(req.body.toString());
    const { reference, transaction } = payload;

    // 4. Idempotency
    const existing = await db.findOne('processed_txs', {
      providerTxId: transaction.id,
    });
    if (existing) return;

    // 5. Query provider to confirm
    const verified = await provider.queryTransaction(transaction.id);
    if (verified.status !== transaction.status) {
      console.warn('Webhook says', transaction.status,
                   'query says', verified.status);
      return;
    }

    // 6. Transition order
    if (transaction.status === 'TS') {
      await orders.transition(reference, 'paid');
    } else if (transaction.status === 'TF') {
      await orders.transition(reference, 'failed');
    }

    // 7. Record
    await db.insert('processed_txs', {
      providerTxId: transaction.id,
      reference,
      processedAt: new Date(),
    });
  }
);

module.exports = router;

The 60-second fallback check

When you initiate a charge, schedule a check 90 seconds later:

async function scheduleStatusCheck(order, delayMs = 90000) {
  setTimeout(async () => {
    const current = await db.getOrder(order.id);
    if (current.status !== 'pending') return;

    const verified = await provider.queryTransaction(order.providerTxId);
    if (verified.status === 'TS') {
      await orders.transition(order.id, 'paid');
    } else if (verified.status === 'TF') {
      await orders.transition(order.id, 'failed');
    } else {
      await orders.transition(order.id, 'failed_timeout');
    }
  }, delayMs);
}

Testing checklist

  • Successful payment end to end
  • Failed payment (customer cancels)
  • Timeout (no webhook, no query result)
  • Duplicate webhook (send the same one twice)
  • Invalid signature (should be rejected)
  • Missing env var at startup (should throw)
  • Slow provider response (should retry with backoff)
  • Concurrent webhooks for the same order
