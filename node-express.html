Node.js is JavaScript running outside the browser. Same language you already know from the frontend — but now it can read files, open network ports, connect to databases, and run on a server 24/7.

Why Node exists

In 2009, Ryan Dahl took Google Chrome's V8 JavaScript engine and wrapped it in a runtime that could talk to the operating system. The result: JavaScript could finally run on the backend — one language for the whole stack.

The event loop

Traditional servers (PHP, Ruby on Rails) handle one request per thread. When you have 10,000 concurrent users, you need 10,000 threads and most of them sit idle waiting for databases and network calls.

Node uses a single thread with an event loop. Instead of waiting, it registers a callback and moves on. When the I/O finishes, the callback runs. The result: one Node process can handle tens of thousands of concurrent connections on modest hardware — perfect for APIs.

What Node is not

  • Not a framework — it is a runtime. Express, Fastify, Nest are frameworks built on top.
  • Not for CPU-heavy work — image processing, video encoding, and heavy math block the event loop. Use workers or another language for those.
  • Not a browser — no document, no window, no DOM. Instead you get fs, http, process, and thousands of npm packages.

Your first Node script

// hello.js
console.log("Hello from Node!");

const now = new Date();
console.log("Started at:", now.toISOString());

const numbers = [1, 2, 3, 4, 5];
const sum = numbers.reduce((a, b) => a + b, 0);
console.log("Sum:", sum);

In a real terminal, you would run this with node hello.js. In the sandbox below, click Run and the same script executes.

Node uses the same console.log, the same arrays, the same objects you already know. If you have written any JavaScript in the browser, you are already 80% of the way to writing Node code.

Node's power comes from its module system. Instead of one giant file, you split your code into small modules that each do one thing and expose just what other modules need.

require — importing

You have three sources of modules:

  1. Built-in modules — require('fs'), require('http'), require('path'), require('crypto')
  2. npm packages — require('express'), require('jsonwebtoken') — anything from npmjs.com
  3. Your own files — require('./utils'), require('./routes/users')

module.exports — exporting

Each file starts with an empty module.exports object. Whatever you assign to it is what other files receive when they require() you.

// math.js
function add(a, b) { return a + b; }
function multiply(a, b) { return a * b; }

module.exports = { add, multiply };
// app.js
const math = require('./math');
console.log(math.add(3, 5));        // 8
console.log(math.multiply(4, 6));   // 24

npm — the package manager

npm comes with Node. Three commands to remember:

npm init -y              # creates package.json
npm install express      # installs a package
npm install --save-dev nodemon   # dev-only dependency

Installed packages live in node_modules/, and their versions are recorded in package.json. Never commit node_modules/ to Git — anyone can regenerate it with npm install.

A built-in module you will use often: fs

const fs = require('fs');

fs.writeFileSync('note.txt', 'Hello, Malawi!');
const content = fs.readFileSync('note.txt', 'utf8');
console.log(content);   // "Hello, Malawi!"

In the sandbox, the file system is simulated in memory, so you can practise reading and writing files without touching your real computer.

Every serious Node project is a tree of small modules. Learn to spot when a file is doing too much and split it — that is the single biggest skill for writing maintainable backends.

Raw Node's http module works, but it is verbose. Express wraps it in a clean API that turns every route into a function call. It is the most popular Node framework by far — used by every size of company, from startups to IBM.

Your first server

const express = require('express');
const app = express();

app.get('/', (req, res) => {
  res.send('Hello, Malawi!');
});

app.listen(3000, () => {
  console.log('Server running on port 3000');
});

Three lines of real work:

  • express() — creates the app object
  • app.get(path, handler) — registers a route for GET requests
  • app.listen(port, cb) — starts listening for connections

req and res

Every route handler receives two objects:

  • req — everything about the incoming request: the method, URL, headers, body, query string, URL params
  • res — your tools for sending a response: res.send(), res.json(), res.status(), res.sendStatus()
app.get('/about', (req, res) => {
  res.json({ name: 'TechMountain', city: 'Lilongwe' });
});

app.get('/health', (req, res) => {
  res.status(200).send('OK');
});

How the sandbox works

In the editor below, when you call app.listen(), the sandbox tells the browser that your server is ready. A request client appears below — pick a method, type a path, and click Send. Your route runs, and the response comes back exactly as it would from a real server.

You will never write http.createServer by hand again — Express is the standard. But it is worth knowing that everything Express does, you could do with raw http and about ten times as much code.

Real APIs have dozens of routes with dynamic segments. Express gives you two ways to read what the client sent: URL parameters and query strings.

URL parameters — :name

A segment prefixed with : is a wildcard. It matches any value at that position and stores it in req.params.

app.get('/users/:id', (req, res) => {
  const userId = req.params.id;
  res.json({ userId, name: 'Chisomo' });
});

// GET /users/42  ->  { "userId": "42", "name": "Chisomo" }

You can have multiple parameters:

app.get('/posts/:postId/comments/:commentId', (req, res) => {
  const { postId, commentId } = req.params;
  res.json({ postId, commentId });
});

Note: req.params values are always strings. If you need a number, convert explicitly with Number(req.params.id) or parseInt.

Query strings — ?key=value

Everything after ? in a URL is a query string. Express parses it into req.query automatically.

// GET /search?q=react&page=2
app.get('/search', (req, res) => {
  const q = req.query.q;        // "react"
  const page = req.query.page;  // "2"
  res.json({ q, page, results: [] });
});

Query strings are for filtering, sorting, and paginating. URL params are for identifying a specific resource.

Route order matters

Express matches routes in the order you defined them. This is a bug that catches every beginner:

// WRONG order — /users/new never reaches its handler
app.get('/users/:id', handler1);   // matches first
app.get('/users/new', handler2);   // never runs

// RIGHT order — specific routes first
app.get('/users/new', handler2);
app.get('/users/:id', handler1);
Rule of thumb: put static routes above dynamic ones. If /users/me should have its own handler, it must be registered before /users/:id.

Middleware is the heart of Express. It is a function that runs on every request, with access to req, res, and a next function. It can read the request, modify it, end the response, or pass control to the next middleware.

The signature

function logger(req, res, next) {
  console.log(req.method, req.url);
  next();   // pass control to the next handler
}

Register it with app.use() — it now runs on every request that reaches the server.

express.json() — parsing request bodies

This is the most important built-in middleware. Without it, req.body is undefined when a client sends JSON.

app.use(express.json());

app.post('/users', (req, res) => {
  console.log(req.body);   // the parsed JSON object
  res.json({ received: req.body });
});

It reads the raw body, checks the Content-Type header is application/json, parses the text, and assigns the result to req.body.

express.static() — serving files

app.use(express.static('public'));

Any file inside public/ becomes available at the matching path. public/logo.png becomes GET /logo.png. Essential for serving images, CSS, and client-side JavaScript.

express.urlencoded() — parsing HTML form bodies

app.use(express.urlencoded({ extended: true }));

Form submissions use a different encoding than JSON. This middleware parses them so you can read form fields with req.body.

The order rule

Middleware runs in the order it was registered. So express.json() must come before the routes that read req.body:

app.use(express.json());       // FIRST
app.post('/users', handler);   // then the routes
Forgetting express.json() is the single most common Express bug. If req.body is undefined, that is almost always the cause.

Custom middleware is where you enforce business rules. Anything you would otherwise repeat in every route — checking a token, logging timing, validating an ID — becomes a middleware that runs before the route.

A logging middleware

function logger(req, res, next) {
  const start = Date.now();
  res.on('finish', () => {
    const ms = Date.now() - start;
    console.log(`${req.method} ${req.url} - ${res.statusCode} (${ms}ms)`);
  });
  next();
}

app.use(logger);

The res.on('finish', ...) listener fires after the response is sent — perfect for timing.

A request-level middleware

You can scope middleware to just one path prefix:

function requireAuth(req, res, next) {
  const token = req.headers.authorization;
  if (!token) {
    return res.status(401).json({ error: 'No token provided' });
  }
  req.user = { id: 1, name: 'Chisomo' };  // pretend we decoded it
  next();
}

app.get('/profile', requireAuth, (req, res) => {
  res.json(req.user);
});

Notice requireAuth is passed as the second argument to app.get. It runs first, and only if it calls next() does the route handler run.

Error-handling middleware — 4 arguments

Express distinguishes error handlers by their arity. A middleware with four parameters is treated as an error handler:

app.use((err, req, res, next) => {
  console.error('Error:', err.message);
  res.status(err.status || 500).json({
    error: err.message || 'Something went wrong'
  });
});

Whenever next(err) is called — in any route or middleware — Express skips directly to the error handlers. Put this at the very bottom of your server file, after every route.

Throwing inside async routes

Express 4 does not catch errors thrown in async functions. You must wrap them:

app.get('/users/:id', async (req, res, next) => {
  try {
    const user = await db.findUser(req.params.id);
    res.json(user);
  } catch (err) {
    next(err);   // pass to error handler
  }
});

Express 5 (in beta) fixes this automatically, but for now always use try/catch in async routes.

Three layered rules to remember: middleware runs in order, error handlers must have four arguments, and errors thrown in async code must be forwarded with next(err).

REST is a design convention for mapping HTTP verbs onto CRUD operations. It is not a standard you must obey — it is a pattern the whole industry agreed on so that anyone can guess your API from its routes.

The mapping

  • GET /items — list all items
  • GET /items/:id — get one item
  • POST /items — create a new item
  • PUT /items/:id — replace an item completely
  • PATCH /items/:id — update only some fields
  • DELETE /items/:id — delete an item

Notice: the path stays the same. Only the verb changes. That is REST.

In-memory data

For teaching, we store data in an array. In a real app, this is a database — but the code shape is identical:

const items = [
  { id: 1, name: 'Learn Node', done: true },
  { id: 2, name: 'Build an API', done: false }
];

List and read

app.get('/items', (req, res) => {
  res.json(items);
});

app.get('/items/:id', (req, res) => {
  const id = Number(req.params.id);
  const item = items.find(i => i.id === id);
  if (!item) {
    return res.status(404).json({ error: 'Item not found' });
  }
  res.json(item);
});

Create

app.post('/items', (req, res) => {
  const { name } = req.body;
  if (!name) {
    return res.status(400).json({ error: 'name is required' });
  }
  const newItem = {
    id: items.length ? Math.max(...items.map(i => i.id)) + 1 : 1,
    name,
    done: false
  };
  items.push(newItem);
  res.status(201).json(newItem);
});

Always validate input before touching the data. Return 400 for bad input, 201 for created.

Update

app.put('/items/:id', (req, res) => {
  const id = Number(req.params.id);
  const idx = items.findIndex(i => i.id === id);
  if (idx === -1) return res.status(404).json({ error: 'Not found' });

  const { name, done } = req.body;
  items[idx] = { id, name, done: Boolean(done) };
  res.json(items[idx]);
});

Delete

app.delete('/items/:id', (req, res) => {
  const id = Number(req.params.id);
  const idx = items.findIndex(i => i.id === id);
  if (idx === -1) return res.status(404).json({ error: 'Not found' });

  const removed = items.splice(idx, 1)[0];
  res.json({ deleted: removed });
});
Notice how every route validates its input, checks for not-found, and returns a meaningful status code. This is what separates a toy API from a professional one.

Every HTTP response carries a status code. Getting them right is what tells the client "this worked", "this was your fault", or "this was our fault".

The ones you will use daily

  • 200 OK — success with a body
  • 201 Created — success, and you created something new (POST)
  • 204 No Content — success, no body (often DELETE)
  • 400 Bad Request — the client sent invalid data (missing field, wrong type)
  • 401 Unauthorized — not logged in (no token, bad token)
  • 403 Forbidden — logged in, but not allowed (wrong role)
  • 404 Not Found — the resource does not exist
  • 409 Conflict — the request clashes with current state (duplicate email)
  • 500 Internal Server Error — a bug on your server

Using them correctly

app.post('/users', (req, res) => {
  const { email, name } = req.body;

  if (!email || !name) {
    return res.status(400).json({ error: 'email and name are required' });
  }

  const exists = users.find(u => u.email === email);
  if (exists) {
    return res.status(409).json({ error: 'Email already registered' });
  }

  const user = { id: users.length + 1, email, name };
  users.push(user);
  res.status(201).json(user);
});

Consistent error shape

Pick one shape for errors and use it everywhere:

{ "error": "Email already registered" }

Or with more detail:

{ "error": { "message": "Validation failed", "fields": ["email"] } }

Clients (frontend apps, mobile apps, other services) rely on this consistency. If your 400s sometimes return strings and sometimes objects, every consumer of your API has to write branching code.

Resource naming conventions

  • Use plural nouns for collections: /users, not /user
  • Use the ID for a specific resource: /users/42
  • Nest for relationships: /users/42/posts — the posts belonging to user 42
  • Use kebab-case for multi-word: /blog-posts, not /blogPosts
  • Never use verbs in the URL. /users/42 with DELETE — not /deleteUser
Status codes are the API's way of speaking. A 500 that should have been a 400 makes the frontend team debug your bug. Get them right from the first route.

Storing passwords as plain text is the single worst thing you can do in a backend. It has ended companies. In this lesson, you will learn the correct way from the first line of code.

Never store plaintext

// NEVER DO THIS
const user = { email: 'a@b.mw', password: 'hunter2' };

If your database leaks, every account is compromised — and worse, users reuse passwords, so you have broken their other accounts too.

Hashing, not encrypting

Encryption is reversible. Hashing is a one-way function — the same input always produces the same output, but you cannot go from the hash back to the password.

We use bcrypt — a slow, salted hashing algorithm designed specifically for passwords.

const bcrypt = require('bcrypt');

const hash = bcrypt.hashSync('hunter2', 10);
console.log(hash);
// "$2b$10$K8s..."

The 10 is the cost factor — 210 = 1024 rounds of hashing. Higher = slower to brute-force. 10 is standard.

What "salted" means

bcrypt generates a random salt for every password and includes it in the hash. Two users with the same password still get different hashes. This defeats rainbow tables — precomputed hashes of common passwords.

Register — hash before saving

app.post('/auth/register', (req, res) => {
  const { email, password } = req.body;

  if (!email || !password) {
    return res.status(400).json({ error: 'email and password required' });
  }

  if (users.find(u => u.email === email)) {
    return res.status(409).json({ error: 'Email already registered' });
  }

  const hashedPassword = bcrypt.hashSync(password, 10);
  const user = { id: users.length + 1, email, password: hashedPassword };
  users.push(user);

  res.status(201).json({ id: user.id, email: user.email });
  // NEVER return the password hash
});

Login — compare, do not decrypt

app.post('/auth/login', (req, res) => {
  const { email, password } = req.body;

  const user = users.find(u => u.email === email);
  if (!user) {
    return res.status(401).json({ error: 'Invalid credentials' });
  }

  const ok = bcrypt.compareSync(password, user.password);
  if (!ok) {
    return res.status(401).json({ error: 'Invalid credentials' });
  }

  res.json({ id: user.id, email: user.email });
});

Notice the error message is identical whether the email is not found or the password is wrong. This prevents email enumeration — an attacker cannot tell which emails are registered.

Three rules to never break: never store plaintext, never return the hash, and always respond with the same message for wrong-email and wrong-password.

Once a user logs in, how do you know who they are on the next request? HTTP is stateless — the server forgets everything between requests. The standard answer is a JSON Web Token.

What is a JWT?

A JWT is a string with three parts, separated by dots:

header.payload.signature
  • header — the algorithm (HS256) and type (JWT), base64-encoded
  • payload — the data you want to store, base64-encoded (NOT encrypted — anyone can read it)
  • signature — a hash of the first two parts, signed with your secret key

The signature is what makes it secure. Without your secret, nobody can forge a valid token. But anyone can read the payload — so never put a password or a credit card number in it.

Signing

const jwt = require('jsonwebtoken');
const SECRET = 'a-long-random-string-stored-in-env';

const token = jwt.sign(
  { userId: 42, email: 'a@b.mw' },
  SECRET,
  { expiresIn: '7d' }
);
res.json({ token });

Verifying

try {
  const payload = jwt.verify(token, SECRET);
  console.log(payload.userId);   // 42
} catch (err) {
  // invalid signature, expired, or malformed
  console.log('Bad token:', err.message);
}

Auth middleware

Wrap the verification in middleware so any protected route can use it:

function requireAuth(req, res, next) {
  const header = req.headers.authorization;
  if (!header || !header.startsWith('Bearer ')) {
    return res.status(401).json({ error: 'No token provided' });
  }

  const token = header.slice(7);   // remove "Bearer "
  try {
    const payload = jwt.verify(token, SECRET);
    req.user = payload;            // make user available to the route
    next();
  } catch (err) {
    res.status(401).json({ error: 'Invalid or expired token' });
  }
}

Protecting routes

app.get('/me', requireAuth, (req, res) => {
  res.json({ user: req.user });
});

app.post('/posts', requireAuth, (req, res) => {
  // req.user is guaranteed here
  const post = { id: posts.length + 1, authorId: req.user.userId, ...req.body };
  posts.push(post);
  res.status(201).json(post);
});

The client flow

  1. Client sends email + password to POST /auth/login
  2. Server returns a JWT
  3. Client stores it (localStorage, or a cookie)
  4. On every subsequent request, client sends Authorization: Bearer <token>
  5. Server verifies the token on each protected route
Never trust the payload blindly. Always verify the signature. An unverified JWT is just base64-encoded JSON that anyone can forge.

Code that works on your laptop and code that runs in production are different things. This lesson covers the professional patterns that separate hobby projects from real ones.

Environment variables

Never hardcode secrets, ports, or API keys. Put them in environment variables:

const PORT = process.env.PORT || 3000;
const SECRET = process.env.JWT_SECRET;

app.listen(PORT, () => console.log(`Listening on ${PORT}`));

Locally, you load them from a .env file using the dotenv package:

require('dotenv').config();
// Now process.env.JWT_SECRET is populated from .env
# .env file — NEVER commit this to Git
PORT=3000
JWT_SECRET=some-long-random-string
DATABASE_URL=mongodb://localhost:27017/myapp

Add .env to .gitignore. On the server (Heroku, Railway, Render, etc.), you set the same variables in their dashboard.

Structured logging

console.log is fine for learning. In production, use a logger that adds timestamps, levels, and JSON output for log aggregation services:

function log(level, message, meta = {}) {
  console.log(JSON.stringify({
    time: new Date().toISOString(),
    level,
    message,
    ...meta
  }));
}

log('info', 'Server started', { port: 3000 });
log('error', 'Failed to save user', { userId: 42, reason: 'duplicate' });

JSON logs are searchable and filterable in tools like Datadog, Loggly, and CloudWatch.

Centralized error handling

Every route should forward errors to a single handler. That handler logs them and returns a consistent shape:

app.use((err, req, res, next) => {
  log('error', err.message, { stack: err.stack, url: req.url });
  res.status(err.status || 500).json({
    error: err.message || 'Internal server error'
  });
});

Graceful shutdown

process.on('SIGTERM', () => {
  console.log('Shutting down gracefully…');
  server.close(() => {
    console.log('Closed out remaining connections');
    process.exit(0);
  });
});

When a deploy or restart happens, the platform sends SIGTERM. Handling it lets in-flight requests finish before the process dies.

The production checklist

  • All secrets in process.env, never hardcoded
  • .env in .gitignore
  • Centralized error handler at the bottom of the file
  • Meaningful log messages with context
  • Health-check endpoint (GET /health) returning { ok: true }
  • Graceful shutdown on SIGTERM
  • Input validation on every route that reads req.body or req.params
A production API is just a toy API with all the boring safety nets added. Nothing here is optional in a real job.

Time to build. Over the final lesson, you will build a complete blog API — full CRUD for posts, JWT auth protecting writes, and in-memory storage that works inside the sandbox. Everything you have learned gets used.

What the API does

  • POST /auth/register — create an account (email + password, password hashed)
  • POST /auth/login — return a JWT
  • GET /posts — list all posts (public)
  • GET /posts/:id — read one post (public)
  • POST /posts — create a post (protected)
  • PUT /posts/:id — update a post (protected, only the author)
  • DELETE /posts/:id — delete a post (protected, only the author)

The data shape

const users = [
  // { id, email, password: "hash", createdAt }
];

const posts = [
  // { id, title, body, authorId, createdAt }
];

Simple, JSON-friendly, easy to filter. In a real project this becomes MongoDB collections or SQL tables.

File structure (in a real project)

server.js
routes/auth.js
routes/posts.js
middleware/auth.js
models/user.js
models/post.js

For the sandbox, everything lives in one file. When you build the real project locally, split it as shown above.

The order of routes

  1. app.use(express.json()) — parse JSON bodies
  2. Auth routes (register, login) — public
  3. GET /posts and GET /posts/:id — public reads
  4. requireAuth middleware
  5. POST /posts, PUT /posts/:id, DELETE /posts/:id — protected
  6. 404 catch-all
  7. Error handler — 4 args, last

Testing in the sandbox

  1. Run the server.
  2. Send POST /auth/register with {"email":"a@b.mw","password":"secret123"}.
  3. Send POST /auth/login with the same credentials. Copy the token from the response.
  4. Send POST /posts with body {"title":"Hello","body":"First post"} and set the Authorization header. In our simple client, we include auth via a special body field _token — the sandbox maps it to req.headers.authorization.
  5. Send GET /posts to see it listed.
  6. Try DELETE /posts/1 with and without the token — see 401 vs 200.

Deploying the real version

  1. Install Node.js and run npm init -y
  2. npm install express bcrypt jsonwebtoken dotenv
  3. Replace in-memory arrays with MongoDB (via Mongoose) or PostgreSQL (via pg)
  4. Push to GitHub
  5. Deploy to Render, Railway, or Fly.io — all have free tiers
  6. Set environment variables in the platform's dashboard
  7. Test with curl or Postman
